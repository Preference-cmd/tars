# Current implementation

TARS is an open-source, local-first AI agent built on Causa (see [README](../README.md)). This page records only the current implementation.

2026-10-26: The shared SessionHost, frozen session definitions, the JSON Store, managed saving and the CLI are wired. `tars session create/run/list` can save a session and reopen the same session across processes; `tars run` uses the same host in transient mode. CLI and TUI prototype share the TOML configuration, and `tars-tui` has sessions, input, temporary streaming text preview, results, cancellation and save recovery wired; workspace tools (three read-only tools plus `write_file`/`edit_file`) and reliable status are wired; a write to an existing file must be preceded by a read, `ask` confirms in the terminal/confirmation panel and refuses in non-terminal contexts, while `accept-edits` and `full-access` do not ask; the four permission modes can be switched while running and are saved with the record, and `tars-tui` has the write confirmation panel, `/mode` command and `Shift-Tab` mode switching wired. MCP is wired through the standalone `mcp.json` configuration (with `${VAR}` expansion and literal-secret checks), preset/CLI/TUI selection, definition snapshots and tool calls through the built-in MCP client; MCP calls run, ask (in the terminal or the TUI confirmation panel) or are rejected according to the `approval` setting in `mcp.json` and the current permission mode. GUI, parent/child agents, installation and release remain in later scope.

The layer is wired into `run_command` (macOS; permission category, definition/configuration and repair list are wired, Linux/Windows fail closed); complete documentation and real use are still step 3.

2026-10-28: Command tool status display is wired: the TUI `/status` shows the sandbox backend and each capability dimension, opening shows the notice when unavailable, and CLI `session create` prints the full status while running a command prints a short status; the TUI confirmation panel and the read-only command summary in the new-session form are covered. Tool-level file, network, signal, timeout/cancel/Drop tests and repair accept/never-rerun tests pass. The SC12 real-model `cargo test` hangs because the sandbox denies `~/.cargo/config.toml` and the Xcode SDK; the policy was not relaxed. The local cargo workaround and sandbox residuals are in [Workspace tools](workspace-tools.md#command-tool).

2026-10-29: The command sandbox changed to whole-machine read-only, credential locations and the current store directory still deny reads and writes, and `/dev` allows only four devices; `.git` was tightened from the whole tree read-only to hooks/config/modules/worktrees read-only with the entry itself not creatable, deletable or renamable, while objects/refs/index are writable again; `network = "open"` was tightened to IP egress plus the system DNS socket. SC02, SC17 and SC18 are checked. [Workspace tools](workspace-tools.md#command-tool) is synchronized.

2026-11-01: Long-session compaction is wired. Every work is assembled with a Causa `ContextPreparer`: before each model round it estimates the request from the last upstream prompt size plus the material added since, and replaces the whole Context with a model-written brief when the estimate crosses `compact_threshold` percent of `context_window` or no longer leaves room for `max_tokens`. A provider context-window failure forces one attempt on the next round even with automatic compaction off. The replaced conversation is written as one `tars-history-v1.1` rewrite record under `<store>/sessions/<id>.history/` and referenced from the record's `history` index; the file is synced before the Context changes, and unreferenced files are removed under the write lock while opening. `auto_compact` and `compact_threshold` are frozen per session with their running values stored in the record only when they differ. Reopening restores the history index; a missing record file is reported only when accessed during expansion. The core manual entry (`ManagedSession::compact`), running settings, history index, expansion and record reads are available to entry points; transient runs keep no history and never compact. Automatic attempts are observed as advisory `Compaction` progress events.

2026-11-01: The command tool's remaining acceptance gaps are closed and its test split is completed. The recording-backend command tests moved out of the macOS-only module into `#[cfg(test)]` modules that run on Linux, macOS and Windows CI, while the real Seatbelt acceptance stays macOS-only. A `#[cfg(test)]`-only probe-failure seam at the host and assembly level (mirroring `CommandRuntime::bind_with_sandbox`) proves that a failed probe leaves the session open with an unavailable command status, rejects every call with the reason and starts no process; the CLI `session create` and TUI startup/`/status` paths show the same fact. `assemble` now binds the command runtime before opening the workspace, so a platform without a backend reports the platform error instead of a workspace error. The `run_command`, permission, definition and repair non-test code contains no `cfg(target_os)` and no Seatbelt vocabulary; capability reports that are unsupported or partially enforced outside the accepted descendant-lifecycle limitation reject before a process starts, and the generated policy contains only canonical absolute paths.

2026-11-01: `search_text` now runs the external `rg` inside a read-only sandbox instead of walking the workspace in-process. It follows the workspace's `.gitignore`, nested ignore files, negation rules and `.ignore` files, never enters `.git`/`.hg`/`.svn`/`.jj`, and supports `regex`, `ignore_case`, `glob` (one bounded glob), `context_lines` (0–3) and `include_ignored`; TARS assembles every argument, with model text only after `--` and inside `--glob=` values, and the version-control exclusions come last. The sandbox policy uses the `Roots` read scope with no network and writes only a private temporary directory; the executable's directory is a policy read root, so the sandbox package does not learn where TARS installs tools. `max_search_depth` maps to `--max-depth` and `max_file_scan_bytes` to `--max-filesize`; `max_search_files`, `max_search_scan_bytes` and the old entry ceiling remain in the definition for record compatibility but no longer bound search. Results take `scanned_files`/`scanned_bytes` from `rg` statistics and turn `rg` stderr into at most 32 issues. A missing backend or unready `rg` rejects the call (never the session) before a process starts. `tars-core::external_tools` resolves the pinned ripgrep 15.2.0 from `[external_tools] rg` (managed, `system` or an absolute path), verifies the managed SHA-256 at startup, caches the check once per process, and installs only after consent (`tars tools status/install rg`, TUI startup check); no other path downloads.

2026-10-31: The sandbox layer moved out of core into the standalone library package `crates/sandbox`, whose dependencies are only `tokio`, `thiserror`, `tempfile` and `rustix` on unix; it depends on neither Causa nor `tars-core`. `tars-core` depends on it and keeps the public `tars_core::sandbox` path in `lib.rs` through `pub use tars_sandbox as sandbox`; CLI/TUI do not depend on it directly. `exit_status_code` became a public function; backend injection, `RecordingBackend` and the function that opens Seatbelt with a given home directory moved into the `test-support` feature (enabled only by `tars-core`'s `[dev-dependencies]`; normal and release builds do not contain them). Sandbox unit tests moved with the package and the workspace test total is unchanged.

2026-11-03: Session metadata and prompt caching are wired. The `tars-session-v2.2` record format adds an optional `title` (the first non-blank line of the first user message, trimmed and whitespace collapsed, at most 80 Unicode scalar values, written on first user block commit and immutable thereafter) and a required `updated_at_ms` (monotonic Unix milliseconds, max(now, prev) updated on every commit). Creation time `created_at_ms` is derived directly from the UUIDv7 ConversationId. CLI `session list` sorts by last activity newest first (unreadable records listed after valid ones, sorted by id), and `--json` includes `title`, `created_at_ms`, and `updated_at_ms`. `session show` displays title, created and last activity times in UTC (`YYYY-MM-DD HH:MM:SS UTC`), and prompt cache setting. `SessionDefinition` gains `prompt_cache: bool` (defaulting to true, frozen at creation), configurable via `--prompt-cache on|off`, TOML `prompt_cache = true|false`, or the TUI `/new` form. When on, requests set `CacheDirective::StablePrefix` on turn run options and compaction brief requests. In the TUI, the `/sessions` picker renders title and last activity on line 1, model on line 2, filtering by title, model, and ID with open sessions displayed first, and `/status` displays prompt cache.

2026-11-04: Compaction summarizes part of the Context instead of all of it. The leading system blocks, the tool state and earlier briefs form a head that is never rewritten; the newest material from a cut point (a user message or the end of a tool round) is kept verbatim within a budget of a quarter of the trigger line left after the fixed prefix, at most 20,000 tokens; the running work's input is protected from its first round on. The brief request is the previous request up to the cut point plus one instruction. A fixed prefix over half the trigger line abandons compaction as `prefix_too_large`, reported once per session. A brief chain over `max((line − prefix) / 8, min(4,000, (line − prefix) / 2))` tokens (an eighth of what the trigger line leaves after the fixed prefix, with a 4,000-token floor capped at half of that remaining space), or over eight briefs, is merged into one brief right after a summary, in a separate `merge` record whose brief points at the earlier ones. Every rewrite removes the sealed provider items (thinking, reasoning) of the replies after its first change in the same record, and a tool round still in progress whose replies carry them is summarized instead of kept in the tail. A brief request is trimmed only when its material is over the window itself.

2026-11-05: The TUI shows a partial rewrite made during the session without reading record files. The conversation is the history expansion of the current Context: the fixed prefix stays at the top of the current part, and a request or reply that a rewrite put back or stripped of its thinking is shown once, through the expansion. Records written in this process (up to 64) are kept in memory and replayed when the record index changes, including a summary followed by a merge and an automatic compaction inside a work; reopening and loading all history shows the same conversation. A rewrite's divider now stands right after the material it summarized, before replies it only stripped. A rebuild while the user is scrolled up keeps the viewed rows in place, and `/summary` shows every brief in the chain, oldest first.

2026-11-05: Two checks avoid wasted brief calls. A brief or merge reply that calls a tool is abandoned as `tool_call`, even when it also has text, and both instructions now ask for text only. After an automatic summary is abandoned as `no_shrink` once its brief came back, later automatic rounds skip the brief call while a brief of that size still could not make the edit smaller, for example when the request in progress is most of the Context; forced and manual compaction are not affected.

2026-11-20: Temporary frame trimming is wired as the fallback when a round's full frame exceeds a known `context_window` (`estimate + max_tokens > context_window`)—on abandoned or insufficient compaction (including `prefix_too_large`), when `auto_compact` is off, and in transient `tars run` sessions with a known window (without creating `.history/` or `.artifacts/`). Trimming operates on a copy of the frame without touching Context or history, drops whole oldest intervals at cut points after the head while preserving protected work inputs, folds dropped tool declarations, drops any middle `Role::System` block that would become adjacent to the fixed prefix, strips sealed provider items from kept replies after the first change, emits `CompactionProgress::Trimmed`, and surfaces notices in CLI stderr and the TUI notice area.

2026-11-21: Unified session prelude (`tars-core::prelude`) and multi-directory skills (`tars-core::skills`) are wired. New sessions and transient `tars run` invocations inject a deterministic two-region prefix: a static `Role::System` region (`tars:prelude:base` plus optional frozen `tars:prelude:static-custom`) followed by a dynamic `Role::User` region (`user-instructions`, `workspace-instructions`, `<available_skills>`, `<env>`, and optional `dynamic-custom`), bounded by a unified 24 KiB budget tightened for small context windows. Mid-session and reopened changes to `AGENTS.md`, `dynamic_context_file`, discovered skills, or permission mode append `tars:prelude:update:<sec>` blocks at the tail to preserve prompt caches and are folded back into the dynamic prefix during compaction (with `trim_frame` protecting the latest update per section). When skills are enabled and at least one valid skill is discovered, the static-schema read-only `load_skill` tool is bound (the 8th built-in tool alongside the 6 workspace tools and persistent `recall`), and loaded `tars:skill` content is protected across compaction within a bounded budget. Session records use `tars-session-v2.3` (rejecting `v2.2` and older), `title` derivation skips `tars:prelude:*`, `tars:compaction`, and `tars:skill` blocks, `session show` runs read-only without credentials and includes prelude/skills summaries, and `tars-tui` folds prelude prefixes, dynamic updates, and preserved skill blocks in the current transcript.

2026-11-22: Tool lifecycle and permission control are rebuilt around TARS-owned classification, tool-owned preflight, and a unified pre-dispatch orchestrator. The acyclic leaf module `tars-core::policy` carries shared permission vocabulary (`PermissionMode`, `ToolPermissionClass`, `PermissionDecision`, `PermissionDecisionKind`, `WriteAction`, `RuleScope`, `RuleSource`, `decide`, `escape_untrusted_text`), while `PermissionHub` moves from `Session` to `application` session entries (`crates/core/src/permission.rs` keeps public re-exports so CLI/TUI stay unchanged). `BuiltinTool` (`definition/workspace.rs`) is the single identity source for all 9 built-in tools (the 6 `WorkspaceTool` variants plus `Recall`, `LoadSkill`, and `RunCode`), eliminating `Tool::hints()` overrides on direct built-in tools and covering `recall`/`load_skill`/`run_code` in MCP name-collision checks (`mcp/source.rs`) and exhaustive repair inspection (`application/repair/inspect.rs`). All tools implement `ManagedTool` (`tools/lifecycle.rs`) with `classify → prepare → approve → commit_prepared → execute`: write and command preflight (including single-pass JSON decoding and single `CommandRuntime::check`) live inside `tools/` with private per-work `WorkStaging` and single-call `ExecutionGrant`, eliminating cross-layer staging and session-wide outside-sandbox grant tables. The single `before` processor `ToolPolicyProcessor` (`permission/orchestrator.rs`) replaces the three separate pre-dispatch processors, validates tool binding against `ctx.tools` so unselected built-in tools settle consistently as `Unavailable`, drops/rolls back prepared state on any rejection, mode switch, missing confirmation route, or cancellation, and commits `WorkStaging` entries only upon approval.

2026-11-23: Sandboxed read-only programmatic tool calling (`run_code`) is wired on top of `rquickjs 0.14.0` (`default-features = false, features = ["futures"]` to eliminate stdout noise on Promise interruption) with zero `unsafe` in TARS code. `SessionDefinition.code_execution: Option<CodeExecutionSettings>` stays opt-in (default off, backward-compatible with older records that omit it) and is configurable via `[code_execution]`, `[profiles.<name>.code_execution]`, CLI `--code-execution` / `--no-code-execution`, and the TUI `/new` form and startup flags; `assembly` omits `run_code` when no read-only workspace tool, `recall`, or `mcp` runtime is bound. `RunCodeTool` executes stateless ES2020 async scripts inside a `spawn_blocking` single-threaded Tokio runtime + `LocalSet`, classifies as `KnownReadOnly`, passes through the outer `before`/`after` processor chain (`ToolPolicyProcessor` + `OutputSpillProcessor`), and dispatches inner read-only subcalls directly to the session's real `WorkspaceTools` (updating shared `observations`), `RecallTool`, and `McpRuntime` (`await tools.list()`, `await tools.describe(name)`, `await tools.call(name, args)` with per-call live `McpPermissionTable` `KnownReadOnly` verification) without touching `ToolProgressSnapshot` or inner `OutputSpillProcessor`. See [Code execution](workspace-tools.md#code-execution-run_code) and [Configuration](configuration.md#code-execution).

2026-11-23: Adopted `causa 0.3` (`ToolMetadata`, `CallAttachments`, and `causa::extension::McpToolAnnotations`) across the tool lifecycle. Every built-in tool (`WorkspaceToolImpl`, `RecallTool`, `LoadSkillTool`, `RunCodeTool`) exposes its `Arc<dyn ManagedTool>` via `Tool::metadata()`, and `McpServerSource::refresh` reads `McpToolAnnotations` from `ToolDescription::metadata` and attaches `McpToolAdapter` (`Arc<dyn ManagedTool>`) directly to each bound `ToolDescription`, eliminating the parallel `ToolCatalog` / `DynamicToolCatalog` tables (`McpPermissionTable` remains solely for `run_code`'s read-only MCP progressive discovery). `ToolPolicyProcessor` looks up tools via `ProcessorContext::tool` and `ProcessorContext::tool_metadata::<Arc<dyn ManagedTool>>`, attaches approved preflight payloads (`PreparedWrite`, `(PreparedCommand, ExecutionGrant)`, validated `run_code` source) to pending calls via `ToolCallEntry::attachments_mut()` (`ManagedTool::attach_prepared`), and clears pending attachments on cancellation while `ToolBatch::resolve_at` atomically clears them on resolution—eliminating per-work `WorkStaging` and `RunCodeTool` staging maps.

2026-11-23: Unified work outcome descriptions and typed assembly errors in `tars-core`. `tars_core::application::WorkOutcome` (`WorkOutcome::of(&WorkResult)`) defines the single core vocabulary (`kind`, `summary`, `hint`, `model_failure`, `detail`) consumed by both CLI (`tars run`, `tars session run`) and `tars-tui`, removing duplicated `TurnInterruption` and `ModelFailure.kind` branching at entry points. `AssemblyError` (including `McpStart(#[source] Arc<McpStartError>)` with `server_id()` / `reason()`) is public and preserved directly in `ApplicationError::Assembly(#[source] AssemblyError)` and downcast in `WorkOutcome::of` for `WorkResult::AssemblyFailed`, so missing credentials, workspace/sandbox unavailability and required MCP startup failures surface specific causes and hints instead of generic failure text. Both `tars run --json` and `tars session run --json` retain existing `status` values (`not_started`, `completed`, `failed`, `cancelled`, `timed_out`) and all existing top-level keys, and add the top-level `kind` field from `WorkOutcome::kind` (`completed`, `cancelled`, `timed_out`, `max_tokens`, `context_window_exceeded`, `refused`, `stop_unrecognized`, `max_model_rounds`, `max_tool_calls`, `model_failed`, `prepare_failed`, `tool_catalog_failed`, `tool_processing_failed`, `unknown_tool_outcome`, `context_commit_failed`, `assembly_failed`, `faulted`, or `failed` for future unrecognized interruptions). CLI exit codes remain `0` (`completed`), `1` (configuration, execution or save failure), `2` (argument error), `124` (`timed_out`) and `130` (`cancelled`). When `kind` is `context_window_exceeded`, CLI attaches `tars session compact` guidance and `tars-tui` displays a `/compact` notice.

2026-11-24: Zero-LLM micro-compaction (`tars-core::compact::micro`, `RewriteKind::MicroCompact`, `kind: "micro-compact"`) is wired alongside `tars-session-v2.4` and `tars-history-v1.2` (refusing `v2.3` and older session records and `v1.1` and older history records without migration). Inside `head_end..k`, `micro::plan` replaces eligible `ToolResult` blocks (`> 400` tokens, or `> 200` tokens for superseded `read_file` results; excluding protected inputs, `load_skill`/`tars:skill`, `media` attachments, open tool rounds carrying sealed thinking, and unseen trailing tool results) with single-line stubs pointing at `<record_id>/<orig_block_id>` or inheriting existing `artifact:<id>` references, while stripping sealed items after the first change in the same `commit_rewrite` edit. Two cache-safety gates prevent thrashing: Path A pre-empts `Auto`/`Passive` LLM summaries only when `saved_tokens >= 2,000`, `estimate_after <= 75%` of trigger line, `estimate_after + max_tokens <= window`, and (when cache is hot) `saved_bytes >= suffix_after_bytes`; Path B runs opportunistically when `auto_compact` is on, `last_call` is at least 5 minutes old, and savings reach `>= 4,000` tokens and `>= 25%`; manual `/compact` and `tars session compact` always run LLM summarization. `BlockStatus::MicroCompacted` (`micro_compacted` in JSON) and `ExpansionCursor` restore originals in place without a divider and expand recursively across `Summarize -> MicroCompact`; `CompactionProgress::MicroCompacted` surfaces a live TUI notice (while CLI stderr stays quiet), `tars-tui` opens with zero record/artifact reads, keeps micro-compacted previews once in the current conversation, loads full outputs on demand in `/tools` (`"Model sees cleared preview only"`), and preserves scroll anchors across live rebuilds, and CLI `session history` / `session show` render and count `micro_compacted` blocks and records.

2026-11-25: SQLite v3 session persistence and event-driven multi-agent collaboration are wired. Session storage migrates from per-session JSON files to `<store>/tars.db` (`rusqlite` `bundled` + WAL + `BEGIN IMMEDIATE` Transactional Outbox across 7 normalized tables: `sessions`, `agents`, `operations`, `agent_events`, `history_records`, `artifacts`, `workspace_trust`) paired with `<store>/locks/<uuid>.lock` OS advisory write locks and lock-free WAL read-only snapshots (`list`, `inspect`, `inspect_agent`, `read_saved_history`), plus explicit `tars session import-legacy` for validated `tars-session-v2.4` JSON records. Inside each session instance, `SessionCoordinator` (`application/coordinator/`) and `BackgroundTaskRegistry` (`events/`) coordinate a three-plane architecture: Plane 1 (`agent_events` causal mailbox with mid-turn injection inside `CompactionPreparer::prepare` after compaction evaluation and 7-guard idle wakeup with 50 ms sibling debounce, `coalesce_key` folding, and reopen downgrade), Plane 2 (`ManagedSession::subscribe_events` `SessionEvent` broadcast), and Plane 3 (`ApprovalsHub` carrying `(agent_id, agent_name, operation_id)`). Models delegate through four pure event-driven collaboration tools (`spawn_agent`, `message_agent`, `read_agent`, `cancel_agent`) backed by monotonic narrowing (`child <= parent`), built-in `explore`/`general` presets, Markdown `.tars/agents/*.md` discovery with SQLite `workspace_trust` (`kind = "workspace_agents"`), named `[profiles.<name>]` selection, and the `<available_agents>` / `<model_profiles>` dynamic prelude section. CLI `tars run` / `session run` wait for finite background tasks and reactive wakeups to converge (with Ctrl-C cascading cancellation), support `--trust-workspace-agents`, and expose lock-free `session show <id> [--agent]` and `session history <id> [--agent]`. `tars-tui` adds the `/agents` switcher and read-only child agent view, `bg N running` and `viewing agent:` status bar indicators, `[agent: <name>]` approval origin prefixes, the `.tars/agents/*.md` workspace trust prompt, and compact `<task-notification>` rendering.

## Shared application entry points

`SessionHost` exclusively owns the active registry and the underlying Session owners. `PreparedCreate` freezes identity before the async step, and `create/open` are registered and supervised by an independent task; dropping a wait or the `ManagedSession` view does not terminate the operation. `SessionTarget` distinguishes different open instances of the same ConversationId; an old target never acts on a reopened instance.

`ManagedSession` provides submit/observe/wait/cancel, subscribe_progress, status, versioned materials, atomic edit, wait_saved/retry_save and forget. The view does not expose the underlying owner/handle. The host provides explicit Save/DiscardLocal close and a single claim of the original uncommitted ToolBatch. Callers decide who may use the host; it is not a user authentication system.

Continuation after interruption handles materials explicitly through `inspect_repair/plan_repair/apply_repair`. The built-in tool assembly can accept the original result of a controlled interruption, and reopening without the original batch can remove unpaired declarations; new input first passes pairing admission, and new work starts only after the save is confirmed. CLI `session repair` and the TUI F7 key share this behavior; the full conditions, versions and retention boundaries are in [Continuation after interruption](session-continuation.md).

The frozen definition contains provider, model, endpoint, credential environment-variable reference, work deadline, retained capacity, model/tool call limits, plus workspace, tool selection, complete tool and write limits, initial permission mode, MCP snapshot, and frozen prelude/skill settings (`static_custom`, `dynamic_custom`, `config_dir`, `skill_dirs`, `include_workspace_skills`, `skills_enabled`). On open it is validated, resolved once and pinned to resources; creation and reopening do not call the model. Reopening keeps the definition and BlockIds, but work tables, request keys, WorkRefs, terminal states and uncommitted batches are not restored, and old work is never rerun automatically. The default workspace tool catalog is empty; `list_directory`/`read_file`/`search_text`/`write_file`/`edit_file`/`run_command` can be enabled explicitly, `recall` is bound on persistent sessions, and `load_skill` is bound when skills are enabled and at least one skill is discovered. Boundaries and record migration are in [Workspace tools](workspace-tools.md); local evidence lives in the local review tree (not in this repository).

The low-level `session` API is still used by the core and fixture consumers; the product CLI goes through the managed entry points. Its original contracts for deduplication, cancellation, typed results, batches and material return are unchanged.

## Streaming observation

The Session worker uses `TurnRunner::run_streaming`, while the original assembly observer still follows the synchronous borrow contract. The CLI keeps waiting and presents the final result (printing temporary frame-trimming and too-large-prefix notices on stderr when they occur); the TUI subscribes to `ManagedSession::subscribe_progress` before submit. Events are attributed by WorkRef and InvocationId and carry ModelStarted, body Text, ModelOutputReady, bounded tool status, and advisory compaction/trimming progress; tool status is also distinguished by declared BlockId. Currently neither reasoning nor unfinished tool arguments are shown.

The channel belongs to one open instance, has a capacity of 128 items, each body at most 16 KiB, truncated on UTF-8 boundaries with a `truncated` marker; bodies are not copied when there is no subscriber. Slow consumers receive Tokio broadcast Lagged and late subscribers get no history replay; subscribing or dropping an observer never cancels work or changes the final result. Event Arcs retained by the caller do not count against the channel capacity. Reliable terminal states still go through observe/wait and are separate from the losable transient preview.

The TUI processes at most 128 items every 50 ms, cycling through views; it keeps at most 256 KiB of body for the current work and current model round, and explicitly reports falling behind or exceeding the limit. End, failure, cancellation and close clear the preview, and the real conversation updates from the Context actually returned. ModelOutputReady only means the model delivered complete output; it does not mean materials were committed or saved successfully. The preview never enters the Store, material export or recovery files.

## Saving and closing

Execution terminal state and save state are independent facts. A persistent instance blocks new keys and edits after T1 is accepted until the save of the actual returned materials is confirmed; replay with the same key still works, and a conflicting key still returns Conflict. Finished can precede Saved. On failure the original result and pending snapshot are kept, and `retry_save` confirms/retries the same commit without calling the model. Versioned editing validates the candidate first; materials are unchanged when it is rejected, and a success saves automatically.

`close(Save)` waits for cancellation, material return and saving; if saving fails, the owner/lock are kept and saving can be retried. `DiscardLocal` waits for in-flight workers/I/O to stop, confirms the original pending commit operation and then abandons the local content without undoing records already on disk. CloseOutcome returns the facts: committed, uncommitted, not attempted or still unconfirmable, the last keeping the original error. Dropping the last host requests a supervised DiscardLocal cleanup; normal wait-for-settling still requires the Tokio runtime to stay alive, and a hard exit does not guarantee unsaved materials can be recovered.

The CLI persistent run waits for the save after success, failure and controlled interruption. During the save wait, the first Ctrl-C prints a notice on stderr, and the second stops waiting, exports the actual Context through the save-failure path and exits with an error. On save failure it follows the selected behavior: export the actual Context to a random `tars-recovery-<uuid>.json` that never overwrites an existing file, then exit with an error; export failure is reported separately. Transient runs export only with an explicit `--save`.

## Compaction and history

Compaction is TARS policy implemented through Causa's public `ContextPreparer` port: the preparer receives the exclusive Context and the round's actual model/tool settings, and edits are committed independently. The estimator wraps the session's model gateway to remember each successful response's prompt total (uncached input plus cache read and write as reported); without upstream usage (a reopened or just-compacted session) it estimates one token per three serialized bytes. When a round's full frame still exceeds a known `context_window` (`estimate + max_tokens > context_window`), whether after an abandoned or insufficient rewrite, with `auto_compact = off`, or in a transient run with a known window, the preparer trims a copy of the frame via `compact::trim` without touching Context or history (dropping oldest cut-point intervals, keeping head and protected work inputs, folding dropped tool declarations, dropping middle system blocks that would adjoin the fixed prefix, and stripping sealed items after the first change) and emits `CompactionProgress::Trimmed`. The summary request is the round's own frame up to the cut point plus one instruction; it uses the session's own model, render options, output limit (capped at 16k tokens) and cache directive, adds no tools of its own, and is governed by the round's `CallControl`; a cancelled or failed attempt leaves the Context and SQLite `history_records` untouched.

A summary replaces only the interval between the head (the leading system blocks, the tool state and earlier briefs) and the retained tail, around the running work's protected input, as described in [Configuration](configuration.md#long-session-compaction); the pure placement and chain-budget rules live in `compact::segment`, zero-LLM micro-compaction and its hot/cold cache-safety gates live in `compact::micro`, and the removal of sealed provider items lives in `compact::sealed`. Before an automatic or forced summary calls the model (Path A), or opportunistically when `auto_compact` is on and `last_call` is at least 5 minutes old (Path B), `CompactionPreparer` can commit a `RewriteKind::MicroCompact` (`micro-compact`) rewrite that folds eligible old or superseded `ToolResult` blocks inside `head_end..k` into single-line stubs pointing at `<record_id>/<orig_block_id>` or inheriting existing `artifact:<id>` references, emitting `CompactionProgress::MicroCompacted`; manual `/compact` and `tars session compact` always run LLM summarization. A summary inserts a declaration of the tool changes the interval made, when there are any, and one user message whose `meta.source` is `tars:compaction`, so Causa's own check that the prepared frame still declares the round's bound tools passes. A merge replaces the chain between the fixed prefix and the end of the head the same way, with one declaration of its tool changes and the merged brief. Protected blocks are put back with their own ids as the last inserted block of the range that starts at them, so the record format is unchanged. Every rewrite goes through one commit path: it builds the record from the blocks it removes, writes it to the SQLite `history_records` table in `<store>/tars.db`, applies all of its ranges in one Context edit, and only then adds the index entry; the saved index changes with the next confirmed save. A process that dies between writing `history_records` and saving leaves an unreferenced row that the next open removes while holding the write lock. Records are read through the core only; entry points never query the history table directly. Expansion replaces each inserted run with the originals of its own range, recursively (crossing `Summarize -> MicroCompact` as needed), and reads a record only when the walk reaches it; `MicroCompact` rewrites emit no divider and label restored originals as `micro_compacted`, while a put-back block stands for itself and the originals after it, and several records may put the same block back; `ExpansionCursor` lets a display supply records one at a time (and `new_for_prefix` skips live `MicroCompact` entries whose stubs remain in the current tail). The CLI exposes `session compact`, `session history` (the expanded conversation, each block marked `original`, `summarized`, `micro_compacted` (`micro-compacted (<id>)` in text), or `unreadable`, with spilled or micro-compacted artifact ids annotated on tool results; `--json` is one block per line; `--last N` reads only the records the newest N blocks need; an unreadable record is reported and exits 1) and `session show` (usage, settings, record count including `micro-compact` records, retained-work occupancy); the TUI expands the `Summarize`/`Merge` history above the conversation, keeps live `MicroCompact` stubs once in the current conversation with zero reads on open, reads records lazily while scrolling up, reads spilled and micro-compacted tool outputs on demand only when `/tools` expands them, and exposes `/auto_compact`, `/compact` and `/summary`.

The record keeps the frozen definition's initial `auto_compact`/`compact_threshold`, the running values only when they differ, and the ordered `history` index. Material export, recovery exports and `--load` handle the current Context only. Reopening validates the index, keeps BlockIds and the frozen definition, and does not restore work tables or old executions. History and artifact payloads are bounded by the same 64 MiB per-payload read limit as a session record; `history_records` and `artifacts` live in separate normalized tables in `tars.db` alongside `sessions`, so they never appear in session listings.

## Backend and resource boundaries

The local store directory is explicitly given by `--store DIR` or the shared TOML `store`; there is no automatically generated default store path. Primary persistence lives in the SQLite v3 WAL database `<store>/tars.db` (`rusqlite` `bundled`, schema `user_version = 1` across `sessions`, `agents`, `operations`, `agent_events`, `history_records`, `artifacts`, and `workspace_trust`), paired with per-session OS advisory lock files at `<store>/locks/<uuid>.lock` and the `tars-session-v2.4` policy tag. Legacy JSON session files (`tars-session-v2.4`) are never silently rewritten in place; validated legacy records (with their `.history/` and `.artifacts/` directories) can be imported explicitly into SQLite as single-root-agent sessions via `tars session import-legacy`, and older `tars-session-v2.3` / `tars-history-v1.1` records remain explicitly rejected with guidance toward `tars session export-materials`. Session usage totals are saved with the record and restored on reopen; formulas, counting rules, scopes and persistence boundaries are detailed in [Usage statistics](session-lifecycle.md#7-usage-statistics). Credential configuration stores only environment-variable names. User materials are saved as they are.

The OS exclusive lock at `<store>/locks/<uuid>.lock` is held from before reading until local worker/I/O stops. Busy, unsupported or I/O errors are all refused and never degrade to no lock. Commits and multi-agent outbox updates execute inside `BEGIN IMMEDIATE ... COMMIT` transactions behind a bounded `spawn_blocking` / `Semaphore` gate, validating the revision and `last_commit_id` baseline; when confirmation is unclear, the original commit is resolved idempotently without skipping or duplicating operations. Read-only operations (`list`, `inspect`, `inspect_agent`, `read_saved_history`, `read_agent`) query lock-free WAL snapshots without contending with active writers. Lock files are not deleted on close; externally deleting/replacing a lock file is not a supported coordination method.

The read/serialize limit for one record/agent material payload is 64 MiB; this is a payload limit, not a memory budget. Recovery export does not truncate materials: files above the limit are still written completely, but the result explicitly reports that the current version cannot import them directly. The default host has at most 32 opening/active/blocked/closing slots and at most 4 concurrent store operations; each session has at most one pending commit. Multi-agent coordination enforces default resource baselines: delegation depth `1`, at most `2` concurrent active delegated operations per initiating agent and `4` concurrent active child operations per session (without implicit queuing), `16 KiB` prompt limit (`128 KiB` `operations.input_json`), `8 KiB` inline `<task-notification>` body limit, `64 KiB` UTF-8-safe `read_agent` pagination, `16` max automatic idle wakeups per user interaction cycle, and a `50 ms` sibling debounce window when sibling background tasks remain active. The CLI persistent definition retains 256 works by default, and the transient `tars run` definition retains `17` works (1 initial turn plus up to 16 automatic wakeups). When the retained-work sheet is full at admission, the oldest finished records that a caller has already read (through `wait` or `observe`) and that have no unclaimed uncommitted batch are released automatically (and reactive auto-wakeup turns are similarly reclaimable when capacity is tight); unread terminal results and unclaimed batches stay retained, and exhausted capacity is refused explicitly with that cause and the remedy (reopen the session, or claim/adopt the pending batches). A released record can no longer be observed and its request key starts new work instead of replaying the old receipt; the conversation materials are untouched, so displayed history is unchanged. There is no unloading or archival of conversation material.

Retention costs include the current Context, the original materials created at creation, the request's original input, terminal-state/unclaimed batch Arcs, pending and baseline copies, serialization buffers, and copies held by callers. Views/observers held after close may also retain the underlying work tables and materials; the active-slot limit does not bound these externally held objects. list must fully validate each record; scanning and memory still grow with the number of records. In sampled observations, peak RSS was about 6.9/24.9/158.7 MiB for 4.2 KiB/1.13 MiB/9.06 MiB material scenarios, and 93.8 MiB for 8 concurrently active medium sessions. This is a single local experiment and does not extrapolate to a throughput guarantee; reliable CPU cache metrics were not collected either. Raw sizes, latencies, copy/serialization and byte counts are in the local review records.

External media/artifact references are rejected by default. The explicit material extension interface can delegate reference validation to the caller, but the Store never copies assets automatically. The current verification scope is complete old/new records after a local process interruption; it does not promise directory-entry durability after power loss, network filesystem/sync-drive cross-host execution, or exactly-once remote side effects.

## Local checks

```sh
cargo fmt --all --check
cargo clippy --workspace --locked --all-targets -- -D warnings
cargo test --workspace --locked
cargo test -p tars-sandbox
RUSTDOCFLAGS='-D warnings' cargo doc --workspace --locked --no-deps
cargo build -p tars-core --locked
cargo build --workspace --locked --release
./target/release/tars session --help
./target/release/tars tools status
./target/release/tars-tui --help
cargo deny check   # security advisories, licenses, sources; policy in deny.toml
```

Tests use local HTTP, scripted models/tools, real files, processes and deterministic barriers, with no live model credentials. The external-tool download tests use a local HTTPS fixture and never reach GitHub; only the local evidence run downloads the real pinned release. Tests are split by platform: common cases run on every platform; workspace-tool and SIGINT cases compile only on Linux/macOS, Seatbelt command and search acceptance cases compile only on macOS (the recording-backend contract tests for both run everywhere), and the non-macOS creation/rejection cases are `cfg` tests that run on Linux and Windows. CI currently runs Linux and macOS only; Windows is left out of CI for now, so nothing checks that the code still builds or passes its tests there. Tool access is implemented only on Linux/macOS, with this round verified on macOS; Windows has no tool capability, and remote CI on each platform still needs its own platform evidence.

Development helper materials and local scripts stay on the local machine and are not added to the repository or the application distribution.
