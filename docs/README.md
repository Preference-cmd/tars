2026-11-01: Long-session compaction is wired. Every work is assembled with a Causa `ContextPreparer`: before each model round it estimates the request from the last upstream prompt size plus the material added since, and replaces the whole Context with a model-written brief when the estimate crosses `compact_threshold` percent of `context_window` or no longer leaves room for `max_tokens`. A provider context-window failure forces one attempt on the next round even with automatic compaction off. The replaced conversation is written as one `tars-history-v1.1` rewrite record under `<store>/sessions/<id>.history/` and referenced from the record's `history` index; the file is synced before the Context changes, and unreferenced files are removed under the write lock while opening. `auto_compact` and `compact_threshold` are frozen per session with their running values stored in the record only when they differ. Reopening restores the history index; a missing record file is reported only when accessed during expansion. The core manual entry (`ManagedSession::compact`), running settings, history index, expansion and record reads are available to entry points; transient runs keep no history and never compact. Automatic attempts are observed as advisory `Compaction` progress events.

2026-11-03: Session metadata and prompt caching are wired. Creation time `created_at_ms` is derived directly from the UUIDv7 ConversationId. CLI `session list` sorts by last activity newest first (unreadable records listed after valid ones, sorted by id), and `--json` includes `title`, `created_at_ms`, and `updated_at_ms`. `session show` displays title, created and last activity times in UTC (`YYYY-MM-DD HH:MM:SS UTC`), and prompt cache setting. `SessionDefinition` gains `prompt_cache: bool` (defaulting to true, frozen at creation), configurable via `--prompt-cache on|off`, TOML `prompt_cache = true|false`, or the TUI `/new` form. When on, requests set `CacheDirective::StablePrefix` on turn run options and compaction brief requests. In the TUI, the `/sessions` picker renders title and last activity on line 1, model on line 2, filtering by title, model, and ID with open sessions displayed first, and `/status` displays prompt cache.

2026-11-04: Compaction summarizes part of the Context instead of all of it. The leading system blocks, the tool state and earlier briefs form a head that is never rewritten; the newest material from a cut point (a user message or the end of a tool round) is kept verbatim within a budget of a quarter of the trigger line left after the fixed prefix, at most 20,000 tokens; the running work's input is protected from its first round on. The brief request is the previous request up to the cut point plus one instruction. A fixed prefix over half the trigger line abandons compaction as `prefix_too_large`, reported once per session. A brief chain over an eighth of what the trigger line leaves after the fixed prefix, or over eight briefs, is merged into one brief right after a summary, in a separate `merge` record whose brief points at the earlier ones. Every rewrite removes the sealed provider items (thinking, reasoning) of the replies after its first change in the same record, and a tool round still in progress whose replies carry them is summarized instead of kept in the tail. A brief request is trimmed only when its material is over the window itself.

2026-11-05: The TUI shows a partial rewrite made during the session without reading record files. The conversation is the history expansion of the current Context: the fixed prefix stays at the top of the current part, and a request or reply that a rewrite put back or stripped of its thinking is shown once, through the expansion. Records written in this process (up to 64) are kept in memory and replayed when the record index changes, including a summary followed by a merge and an automatic compaction inside a work; reopening and loading all history shows the same conversation. A rewrite's divider now stands right after the material it summarized, before replies it only stripped. A rebuild while the user is scrolled up keeps the viewed rows in place, and `/summary` shows every brief in the chain, oldest first.

## Shared application entry points

`SessionHost` exclusively owns the active registry and the underlying Session owners. `PreparedCreate` freezes identity before the async step, and `create/open` are registered and supervised by an independent task; dropping a wait or the `ManagedSession` view does not terminate the operation. `SessionTarget` distinguishes different open instances of the same ConversationId; an old target never acts on a reopened instance.

`ManagedSession` provides submit/observe/wait/cancel, subscribe_progress, status, versioned materials, atomic edit, wait_saved/retry_save and forget. The view does not expose the underlying owner/handle. The host provides explicit Save/DiscardLocal close and a single claim of the original uncommitted ToolBatch. Callers decide who may use the host; it is not a user authentication system.

Continuation after interruption handles materials explicitly through `inspect_repair/plan_repair/apply_repair`. The built-in tool assembly can accept the original result of a controlled interruption, and reopening without the original batch can remove unpaired declarations; new input first passes pairing admission, and new work starts only after the save is confirmed. CLI `session repair` and the TUI F7 key share this behavior; the full conditions, versions and retention boundaries are in [Continuation after interruption](session-continuation.md).

The frozen definition contains provider, model, endpoint, credential environment-variable reference, work deadline, retained capacity, model/tool call limits, plus workspace, tool selection, complete tool and write limits, initial permission mode and MCP snapshot. On open it is validated, resolved once and pinned to resources; creation and reopening do not call the model. Reopening keeps the definition and BlockIds, but work tables, request keys, WorkRefs, terminal states and uncommitted batches are not restored, and old work is never rerun automatically. The default tool catalog is empty; list_directory/read_file/search_text/write_file/edit_file/run_command can be enabled explicitly. Boundaries and record migration are in [Workspace tools](workspace-tools.md); local evidence lives in the local review tree (not in this repository).

The low-level `session` API is still used by the core and fixture consumers; the product CLI goes through the managed entry points. Its original contracts for deduplication, cancellation, typed results, batches and material return are unchanged.

## Streaming observation

The Session worker uses `TurnRunner::run_streaming`, while the original assembly observer still follows the synchronous borrow contract. The CLI keeps waiting and presents the final result; the TUI subscribes to `ManagedSession::subscribe_progress` before submit. Events are attributed by WorkRef and InvocationId and carry ModelStarted, body Text, ModelOutputReady and bounded tool status; tool status is also distinguished by declared BlockId. Currently neither reasoning nor unfinished tool arguments are shown.

The channel belongs to one open instance, has a capacity of 128 items, each body at most 16 KiB, truncated on UTF-8 boundaries with a `truncated` marker; bodies are not copied when there is no subscriber. Slow consumers receive Tokio broadcast Lagged and late subscribers get no history replay; subscribing or dropping an observer never cancels work or changes the final result. Event Arcs retained by the caller do not count against the channel capacity. Reliable terminal states still go through observe/wait and are separate from the losable transient preview.

The TUI processes at most 128 items every 50 ms, cycling through views; it keeps at most 256 KiB of body for the current work and current model round, and explicitly reports falling behind or exceeding the limit. End, failure, cancellation and close clear the preview, and the real conversation updates from the Context actually returned. ModelOutputReady only means the model delivered complete output; it does not mean materials were committed or saved successfully. The preview never enters the Store, material export or recovery files.

## Saving and closing

Execution terminal state and save state are independent facts. A persistent instance blocks new keys and edits after T1 is accepted until the save of the actual returned materials is confirmed; replay with the same key still works, and a conflicting key still returns Conflict. Finished can precede Saved. On failure the original result and pending snapshot are kept, and `retry_save` confirms/retries the same commit without calling the model. Versioned editing validates the candidate first; materials are unchanged when it is rejected, and a success saves automatically.

`close(Save)` waits for cancellation, material return and saving; if saving fails, the owner/lock are kept and saving can be retried. `DiscardLocal` waits for in-flight workers/I/O to stop, confirms the original pending commit operation and then abandons the local content without undoing records already on disk. CloseOutcome returns the facts: committed, uncommitted, not attempted or still unconfirmable, the last keeping the original error. Dropping the last host requests a supervised DiscardLocal cleanup; normal wait-for-settling still requires the Tokio runtime to stay alive, and a hard exit does not guarantee unsaved materials can be recovered.

The CLI persistent run waits for the save after success, failure and controlled interruption. During the save wait, the first Ctrl-C prints a notice on stderr, and the second stops waiting, exports the actual Context through the save-failure path and exits with an error. On save failure it follows the selected behavior: export the actual Context to a random `tars-recovery-<uuid>.json` that never overwrites an existing file, then exit with an error; export failure is reported separately. Transient runs export only with an explicit `--save`.

## Compaction and history

Compaction is TARS policy implemented through Causa's public `ContextPreparer` port: the preparer receives the exclusive Context and the round's actual model/tool settings, and edits are committed independently. The estimator wraps the session's model gateway to remember each successful response's prompt total (uncached input plus cache read and write as reported); without upstream usage (a reopened or just-compacted session) it estimates one token per three serialized bytes. The summary request is the round's own frame up to the cut point plus one instruction; it uses the session's own model, render options, output limit (capped at 16k tokens) and cache directive, adds no tools of its own, and is governed by the round's `CallControl`; a cancelled or failed attempt leaves the Context and the history directory untouched.

A summary replaces only the interval between the head (the leading system blocks, the tool state and earlier briefs) and the retained tail, around the running work's protected input, as described in [Configuration](configuration.md#long-session-compaction); the pure placement and chain-budget rules live in `compact::segment` and the removal of sealed provider items in `compact::sealed`. It inserts a declaration of the tool changes the interval made, when there are any, and one user message whose `meta.source` is `tars:compaction`, so Causa's own check that the prepared frame still declares the round's bound tools passes. A merge replaces the chain between the fixed prefix and the end of the head the same way, with one declaration of its tool changes and the merged brief. Protected blocks are put back with their own ids as the last inserted block of the range that starts at them, so the record format is unchanged. Every rewrite goes through one commit path: it builds the record from the blocks it removes, writes and syncs it, applies all of its ranges in one Context edit, and only then adds the index entry; the saved index changes with the next confirmed save. A process that dies between the file write and the save leaves an unreferenced file that the next open removes while holding the write lock. Records are read through the core only; entry points never open the history directory themselves. Expansion replaces each inserted run with the originals of its own range, recursively, and reads a record only when the walk reaches it; a put-back block stands for itself and the originals after it, and several records may put the same block back; `ExpansionCursor` lets a display supply records one at a time. The CLI exposes `session compact`, `session history` (the expanded conversation, each block marked original, summarized, elided or unreadable; `--json` is one block per line; `--last N` reads only the records the newest N blocks need; an unreadable record is reported and exits 1) and `session show` (usage, settings, record count, retained-work occupancy); the TUI expands the history above the conversation, reads records lazily while scrolling up and exposes `/auto_compact`, `/compact` and `/summary`.

The record keeps the frozen definition's initial `auto_compact`/`compact_threshold`, the running values only when they differ, and the ordered `history` index. Material export, recovery exports and `--load` handle the current Context only. Reopening validates the index, keeps BlockIds and the frozen definition, and does not restore work tables or old executions. History is bounded by the same 64 MiB per-file read limit as a record; the directory adds no entry to session listings because only `*.json` record files are listed.

## Backend and resource boundaries

The local store directory is explicitly given by `--store DIR` or the shared TOML `store`; there is no automatically generated default store path. Records live at `DIR/sessions/<uuid>.json` in the `tars-session-v2.2` format; `workspace_root`, `tools`, `tool_limits`, and `updated_at_ms` are required, while write limits, initial/current permission mode, the MCP snapshot, running compaction values, the history index, session usage totals, and `title` may be omitted, in which case the default write limits, `ask`, no servers, the definition's compaction values, no history, zero usage, and no title are read. Older records (`tars-session-v2.1` and older, and `tars-history-v1` segments) are refused with an error stating the file's version and the supported version, leaving file bytes and mtime unchanged; `session list` lists such records as invalid with that reason, and the hint toward `tars session export-materials` stays (no migration). Session usage totals are saved with the record and restored on reopen; formulas, counting rules, scopes and persistence boundaries are detailed in [Usage statistics](session-lifecycle.md#7-usage-statistics). The frozen definition, Context, ConversationId, revision and last_commit_id are written in one step; the initial revision is 1. Credential configuration stores only environment-variable names. User materials are saved as they are.

A stable `<uuid>.lock` file is separate from the replaceable record, and the OS exclusive lock is held from before reading until local worker/I/O stops. Busy, unsupported or I/O errors are all refused and never degrade to no lock. A commit validates the baseline and the full content, then uses a same-directory temporary file, content flush and atomic replacement; when confirmation is unclear the original operation is kept. list ignores locks and temporary files and reports corruption and active status per record; a listing is not an atomic snapshot of the whole directory.

The read/serialize limit for one record is 64 MiB; this is a file limit, not a memory budget. Recovery export does not truncate materials: files above the limit are still written completely, but the result explicitly reports that the current version cannot import them directly. The default host has at most 32 opening/active/blocked/closing slots and at most 4 concurrent store operations; each session has at most one pending commit. The CLI persistent definition retains 256 works by default, and the transient definition retains 1. When the retained-work sheet is full at admission, the oldest finished records that a caller has already read (through `wait` or `observe`) and that have no unclaimed uncommitted batch are released automatically; unread terminal results and unclaimed batches stay retained, and exhausted capacity is refused explicitly with that cause and the remedy (reopen the session, or claim/adopt the pending batches). A released record can no longer be observed and its request key starts new work instead of replaying the old receipt; the conversation materials are untouched, so displayed history is unchanged. There is no unloading or archival of conversation material.

Retention costs include the current Context, the original materials created at creation, the request's original input, terminal-state/unclaimed batch Arcs, pending and baseline copies, serialization buffers, and copies held by callers. Views/observers held after close may also retain the underlying work tables and materials; the active-slot limit does not bound these externally held objects. list must fully validate each record; scanning and memory still grow with the number of records. In sampled observations, peak RSS was about 6.9/24.9/158.7 MiB for 4.2 KiB/1.13 MiB/9.06 MiB material scenarios, and 93.8 MiB for 8 concurrently active medium sessions. This is a single local experiment and does not extrapolate to a throughput guarantee; reliable CPU cache metrics were not collected either. Raw sizes, latencies, copy/serialization and byte counts are in the local review records.

External media/artifact references are rejected by default. The explicit material extension interface can delegate reference validation to the caller, but the Store never copies assets automatically. The current verification scope is complete old/new records after a local process interruption; it does not promise directory-entry durability after power loss, network filesystem/sync-drive cross-host execution, or exactly-once remote side effects.

Tests use local HTTP, scripted models/tools, real files, processes and deterministic barriers, with no live model credentials. The external-tool download tests use a local HTTPS fixture and never reach GitHub; only the local evidence run downloads the real pinned release. Tests are split by platform: common cases run on every platform; workspace-tool and SIGINT cases compile only on Linux/macOS, Seatbelt command and search acceptance cases compile only on macOS (the recording-backend contract tests for both run everywhere), and the non-macOS creation/rejection cases are `cfg` tests that run on Linux and Windows. CI currently runs Linux and macOS only; Windows is left out of CI for now, so nothing checks that the code still builds or passes its tests there. Tool access is implemented only on Linux/macOS, with this round verified on macOS; Windows has no tool capability, and remote CI on each platform still needs its own platform evidence.

Development helper materials and local scripts stay on the local machine and are not added to the repository or the application distribution.
