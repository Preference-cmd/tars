# Workspace tools

TARS can explicitly enable seven built-in workspace tools for a new session: the read-only `list_directory`, `read_file`, `search_text`, and `find_files`, the write tools `write_file` and `edit_file`, and `run_command`. `find_files` performs pure-Rust handle-relative glob discovery on both macOS and Linux with zero external binary dependencies, `search_text` runs the external [`ripgrep`](https://github.com/BurntSushi/ripgrep) (`rg`) executable inside a read-only sandbox, and `run_command` executes commands inside the platform OS sandbox (macOS Seatbelt or Linux Bubblewrap `bwrap` + `seccomp-BPF`). CLI and TUI share the core's configuration, actual tools and resource supervision; model round trips are still executed by the Causa runner. The default workspace tool catalog is empty (while interactive TUI default session startup and the `/new` form default to all 7 tools when the sandbox is available and fall back to the 5 non-sandboxed tools on Linux when `bwrap` / unprivileged user namespaces are unavailable), and merely setting a workspace enables no workspace tools. In addition to workspace tools, TARS provides three built-in non-workspace read-only tools (all 10 built-in tools are uniformly defined by `tars_core::definition::BuiltinTool`): `recall`, automatically bound in every persistent session for inspecting compacted history and spilled artifacts (see [Long-session compaction](configuration.md#compaction-recall-tool)), `load_skill`, automatically bound whenever skills are enabled (`skills_enabled = true`, not `--no-skills`) and at least one valid skill is discovered in the configured (`~/.tars/skills` / `$TARS_HOME/skills` by default) or workspace-private (gitignored) `.tars/skills` directories (see [Session prelude and skills](configuration.md#session-prelude-and-skills)), and `run_code`, an opt-in ES2020 QuickJS sandbox for read-only programmatic tool calling (see [Code execution](#code-execution-run_code)).

```sh
tars run --provider openai-chat --model "$MODEL_ID" \
  --workspace . --tools list_directory,read_file,find_files,search_text \
  --input 'Find the recovery path after a save failure and give the file and line numbers'
tars session create --store ./data --provider openai-chat --model "$MODEL_ID" \
  --workspace . --tools list_directory,read_file,search_text,find_files,write_file,edit_file,run_command \
  --command-network none --permission-mode ask --json
```

The shared TOML preset's `workspace_root`, `tools`, `permission_mode` and `mcp` fill the interactive TUI new-session form; the TUI does not offer these startup arguments. The form provides Workspace, Tools, permission mode and MCP fields; `--tools ''` or clearing the form's Tools field disables the preset tools. When the current Tools include `run_command`, the form also shows a read-only `command` summary line (network, default deadline and maximum), which cannot be edited. A saved session freezes the workspace, selection and complete limits; reopening uses the original definition and does not change with configuration or cwd. A missing root directory, or one that no longer satisfies the access rules, makes opening fail without falling back to the current directory and without sending a model request.

`search_text` does not search in-process: it runs the resolved `rg` in a read-only sandbox, so it follows the workspace's `.gitignore`, nested ignore files and negation rules, and never descends into `.git`, `.hg`, `.svn` or `.jj`; a search path naming one of them is rejected. `rg` is not bundled with TARS and is never downloaded silently: `tars tools status` shows the resolved source, path, version and state, and `tars tools install rg [--yes]` asks before downloading the pinned `15.2.0` release (macOS `aarch64`/`x86_64`, Linux `x86_64`/`aarch64`, verified against the SHA-256 compiled into TARS). `[external_tools] rg` defaults to `auto` (preferring a verified managed copy, falling back to `rg >= 14` on `PATH`, or prompting/failing closed if neither is usable) and can also be set to `managed`, `system`, or an absolute path. `search_text` is supported on macOS (Seatbelt) and Linux (`bwrap` + `seccomp-BPF`, requiring `bubblewrap` and unprivileged user namespaces) and fails closed on Windows until a Windows sandbox backend exists; a saved session or preset containing `search_text` still opens when unavailable and rejects every search call with the missing reason. The complete contract, ignore rules, limits and residuals are in [Search tool](#search-tool).

`run_command` launches `/bin/bash -c` inside the sandbox by default, with no network, a writable workspace, read-only `.git` hooks and configuration, read-only `<workspace_root>/.tars/` and any in-workspace session store directory, and unreadable/unwritable credential locations. The confirmation panel for sandboxed commands shows the full command, working directory, deadline and network policy, while a sandbox-outside request instead shows a warning and the justification. Permissions are handled according to the four modes: `read-only` rejects; `ask` asks; `accept-edits` executes sandboxed commands directly and still asks for sandbox-outside requests; `full-access` executes both directly. A single command can request running outside the sandbox with a justification, and without such a request the command always stays inside the sandbox. `run_command` is supported on macOS (Seatbelt) and Linux (`bwrap` + `seccomp-BPF`, reporting all 5 capability dimensions `full`); Windows does not support this tool yet. The complete contract, sandbox scope, status display and residuals are in [Command tool](#command-tool).

## File access

When the configuration is first resolved, the selected path is resolved to a physical absolute directory; TOML relative paths are based on the configuration file's directory, and CLI relative paths are based on the cwd at resolution time. An opened instance opens store paths component by component from `/` using directory handles and NOFOLLOW, after which every component is accessed relative to an already opened directory. Linux/macOS provide this implementation; the real-file and terminal evidence from this round comes from macOS, and Linux still needs independent platform verification. Other platforms reject tool enablement explicitly, while sessions without tools remain usable.

Tools accept only non-empty relative paths, with `.` meaning the root directory; they reject absolute paths, any `..`, backslashes, NUL, paths over 4096 bytes, symbolic links, different devices and special files. Files are opened with NONBLOCK and then checked for a regular-file type, so being replaced by a FIFO cannot hang the open. A directory listing may show link entries but does not follow them. Search skips links/special files and reports incompleteness.

An instance is bound to the root directory handle, so replacing a path does not redirect the current instance; an opened subdirectory that is later moved still represents the original resource. This mechanism does not isolate same-device bind mounts or hard links, and it is not a process OS sandbox. A result is an observation from one read, not a cross-file consistent snapshot. Files can change before a later call; the Store saves committed materials and does not back up the workspace. `search_text` is the exception that runs under an OS sandbox, because it delegates traversal to `rg`.

Writes and reads use the same path rules. `write_file` can create a new file inside an existing directory, creating missing intermediate directories component by component through directory handles; when the target already exists it follows the read-before-write check. `write_file` and `edit_file` reject any path with a component named `.git`, `.hg`, `.svn` or `.jj` (ASCII case-insensitive, at any depth, including the entry itself) in every permission mode before confirmation: hooks and configuration there run outside the sandbox the next time the user runs that tool, so an automatically approved write would escape it. They likewise reject `<workspace_root>/.tars/` (and `.tars` itself, ASCII case-insensitive at the workspace root) and any path inside an in-workspace session store directory (including the whole workspace when the store equals or wraps the workspace root) in every permission mode—including `full-access`—before read-before-write checks and confirmation. Reads are unaffected, and names such as `.gitignore`, `.github/` or `.tarsignore` remain writable. A write first creates a temporary file in the same directory, syncs it, re-checks an existing target's metadata immediately before replacement, and then overwrites with `renameat`; a new target uses no-overwrite semantics so a concurrently appearing file is not silently replaced. Because `renameat` replaces the directory entry with the temporary file, it assigns a new inode to the target path and breaks any sharing with other hard links to the previous inode. Existing file permission bits are preserved where possible, and readers see either the old or the new content. When an existing file uses CRLF, its newline style is kept.

## Inputs and results

| Tool | Input | Output |
| --- | --- | --- |
| `list_directory` | `path`, optional `limit` | One level of `entries` (name/type), `truncated`, `limit_reason`; enumeration order is filesystem-defined |
| `read_file` | `path`, optional one-based `start_line` and `max_lines` (default 200, at most 2000) | Requested starting line, actual `end_line` (null when no lines are returned), text, scanned bytes, truncation reason |
| `search_text` | `path` (directory or single file), non-empty single-line `query` (at most 1024 bytes; CR/LF/NUL rejected), optional `regex`, `ignore_case`, `glob` (at most 256 bytes), `context_lines` (0–3), `include_ignored` and `max_matches` | Relative file paths, one-based line numbers, snippets near the match with optional `before`/`after`, scanned file/byte counts from `rg`, at most 32 issues and `complete` |
| `find_files` | All optional: `path` (directory, defaults to `.`), `pattern` (glob at most 256 bytes; CR/LF/NUL rejected), `max_results` (`1..=max_search_matches`), `max_depth` (`1..=max_search_depth`), `ignore_case`, `include_ignored` | Deterministic sorted BFS list of workspace-relative `files`, `path`, `pattern`, `scanned_dirs`, `complete`, `truncated`, `limit_reason`, and at most 32 `issues` |
| `write_file` | `path`, `content` | `path`, `action` (`created` / `updated`), `bytes_written`, `lines_added`, `lines_removed` |
| `edit_file` | `path`, `edits` (each with `old_text`, `new_text`) | Same as above |

Arguments reject unknown fields, wrong types, duplicate/disabled tools and out-of-limit values. The schema is a reference for the model, and actual calls are re-validated. Invalid arguments and forbidden access are Rejected; a missing path, ordinary I/O, NUL binary content or invalid UTF-8 on a valid path are Failed. Reaching a scan/output limit may be Succeeded while the result clearly marks truncation or incompleteness; it never proves that unscanned regions contain no match. `list_directory`, `read_file` and the write tools handle UTF-8 text only; `search_text` delegates matching to `rg` and its own ignore and binary-file handling. Write tools return only a summary to the model, never a diff or the full text.

## Writes and read-before-write

`write_file` takes `path` and `content`; a missing target is created and an existing target is replaced wholesale. Creation needs no prior read; if the target appeared at execution time without having been read, the call is rejected as "exists but not read". Overwriting an existing file requires a prior `read_file` and the current version matching the read. `content` is at most `max_write_bytes` (default 1 MiB), and for an existing file it must also not exceed `max_edit_file_bytes` (default 2 MiB). When an existing file uses CRLF, a lone LF in `content` is written as CRLF.

`edit_file` takes `path` and `edits: [{old_text, new_text}]`. Each `old_text` must occur exactly once in the original file, and segments must not overlap; all replacements are located against the original text and the new content is generated in one step. It performs only exact matching, never fuzzy matching, and offers no `replace_all`. An empty `old_text`, one equal to `new_text`, no match, multiple matches or overlapping segments are all Rejected without showing a confirmation and without touching the file; the error names `edits[i]` and the reason so the model can correct itself. A single call has at most `max_edit_segments` segments (default 32).

An open instance keeps an observation table keyed by file identity (`device id`, `inode`) recording the files `read_file` has read and their versions (device id, inode, size, mtime, content hash); partial reads also count as read, and reading a file through any name (such as a case variant on a case-insensitive filesystem or a hard link) satisfies the read requirement for that file identity. `edit_file` and `write_file` over an existing file require the target's file identity to be in the table and the current version to match the record. A target whose file identity was never read—including when an external process replaced the path with a new file having a different inode—returns Rejected with a hint to use `read_file`; a file modified in place externally after being read returns Rejected with a hint to read again. Because `renameat` atomic replacement gives the target path a new inode (disconnecting it from any other hard links to the previous inode), a successful write removes the old identity entry if different and records the new file identity and version, so editing the same file repeatedly in one open instance needs no re-read. The observation table is not saved; after reopening the session the file must be read again.

The confirmation panel shows the complete diff (3 lines of context); the `/tools` panel expands tool arguments and result summaries, without the diff. The diff is kept only in the open instance and never enters Context or is saved; after reopening only the summary is visible.

## Confirmation and permission modes

"Permission mode" here means TARS's `permission_mode`, which decides which calls need confirmation. The `approval` in an MCP entry is a separate setting that only decides whether that server or tool asks by default; the combination of the two determines the final behavior, see [Configuration](configuration.md#mcp-servers).

| Mode | Known read-only | Built-in writes | Built-in command | Sandbox-outside command | MCP requiring prompt | MCP `approve` |
| --- | --- | --- | --- | --- | --- | --- |
| `read-only` | executes | rejects | rejects | rejects | rejects | rejects |
| `ask` (default) | executes | asks | asks | asks | asks | executes |
| `accept-edits` | executes | executes | executes | asks | asks | executes |
| `full-access` | executes | executes | executes | executes | executes | executes |

"Built-in command" means `run_command`; "sandbox-outside command" means the same call with `outside_sandbox: true` and a justification. Under `accept-edits`, sandboxed commands execute directly (regardless of whether `network` is `none` or `open`), while sandbox-outside requests still ask; under `full-access`, both execute directly. Without a sandbox-outside request the command always stays inside the sandbox, and `full-access` only skips the confirmation.

"Known read-only" means the four built-in read-only workspace tools (`list_directory`, `read_file`, `search_text`, `find_files`), the built-in compaction `recall` tool in persistent sessions (see [Long-session compaction](configuration.md#compaction-recall-tool)), the built-in `load_skill` tool when skills are enabled and available (see [Session prelude and skills](configuration.md#session-prelude-and-skills)), the opt-in `run_code` sandbox when enabled (see [Code execution](#code-execution-run_code)), plus MCP tools declared read-only without a destructive declaration under `approval = "writes"`. TARS classifies its 10 built-in tools independently through TARS-owned `ManagedTool` handles carried in Causa's opaque `ToolMetadata` (`Tool::metadata()`). For remote MCP tools, `McpServerSource` reads server-advertised `causa::extension::McpToolAnnotations` from `ToolDescription::metadata`, overlays the frozen server/tool `approval` setting (`approve` maps to `McpApprove`, `prompt` maps to `McpPrompt`, and `writes` maps tools explicitly annotated `read_only = true` without `destructive = true` to `KnownReadOnly` while mapping unannotated or destructive tools to `McpPrompt`), and attaches the resulting `McpToolAdapter` (`Arc<dyn ManagedTool>`) to `ToolDescription::metadata`. `approve` only answers "should this be asked?", not "the tool has no side effects", so `read-only` still rejects it. `writes` trusts the server's read-only declarations; TARS cannot detect a server that declares a writing tool as read-only, which is the cost of choosing that level.

### Tool lifecycle and policy orchestration

Every tool call in a Causa `ToolBatch` passes through a single `before` orchestrator, `ToolPolicyProcessor` (`permission/orchestrator.rs`), using the `ManagedTool` lifecycle contract (`tools/lifecycle.rs`) carried in Causa `ToolMetadata` and `CallAttachments`: `classify → prepare → approve → attach_prepared → execute`.

1. **Unbound and unselected tool reconciliation**: Before gating, `ToolPolicyProcessor` checks each call against the round's actual bound tool set (`ctx.tool(name)`), including calls already rejected by Causa's unbound-tool check. Any tool not bound in `ctx.tools`—including a built-in tool not enabled for the session—produces the same `tool '<name>' is not available` rejection and records `PermissionDecisionKind::Unavailable`.
2. **Batch-wide zero-I/O fast gate (`classify`)**: In declaration order, `ToolPolicyProcessor` resolves each bound tool's `Arc<dyn ManagedTool>` via `ctx.tool_metadata` and runs `classify(arguments)` with zero disk or process I/O to produce a `ToolCallIntent` (`ToolPermissionClass` plus, for `run_command`, the raw command text for rule matching). `ToolPolicyProcessor` evaluates the live `PermissionMode` and `CommandRuleSet` via `tars-core::policy::decide`; calls that are mode-refused, rule-denied, or require confirmation with no active confirmation route are rejected immediately without reading files or running sandbox checks.
3. **Serial per-call `prepare → re-decide → approve → attach_prepared`**: Remaining calls proceed one by one in declaration order:
   - If cancellation or deadline has triggered, attachments on any pending entries in the batch are cleared, and later calls perform no disk or sandbox I/O.
   - `prepare` runs inside `tools/` (read-only built-in tools and MCP tools use a no-op default). `write_file` and `edit_file` decode JSON once, check workspace boundaries and protected paths, open or probe the target to obtain its `WriteTargetKey` (`(device id, inode)` for existing files, or normalized parent components and file name for new files), run same-batch target deduplication (`BatchPrepareState`) and read-before-write against the observation table, and generate the unified diff into an internal `PreparedWrite`. `run_command` decodes JSON once, validates parameters and policy, and runs `CommandRuntime::check` once. `run_code` validates the JavaScript payload once. Calls failing `prepare` receive `Rejected` or `Failed` immediately without prompting the user. When one batch contains multiple write calls for the same existing file identity (including case variants on case-insensitive volumes and hard links) or the same new-file path, only the first is prepared and the rest are `Rejected` ("the same file can only be modified once in a single batch"); writes to different files execute normally once approved. For new files on case-insensitive filesystems, preflight does not fold case on path components, so two new-file calls differing only by case (such as `Foo` and `foo`) both pass `prepare`; at execution, the second call is intercepted by `NOREPLACE` / `AlreadyExists` and rejected without overwriting the first.
   - After `prepare`, `ToolPolicyProcessor` re-reads the live `PermissionMode` and `CommandRuleSet` and re-evaluates the verdict (capturing mid-batch mode switches or newly added rules).
   - If confirmation is needed, `approval_preview` builds a read-only `ApprovalPreview` from the prepared state without re-decoding raw JSON, and waits on `ApprovalsHub` racing against `CallControl`.
   - **Attachment and grant invariant**: Only upon final authorization (`DirectExecution` or user approval) does `ToolPolicyProcessor` call `attach_prepared` to place the non-persisted `PreparedWrite`, `(PreparedCommand, ExecutionGrant)`, or validated `run_code` source into the call's Causa `CallAttachments` (`ToolCallEntry::attachments_mut()`). On user rejection, mode switch to a disallowing mode, missing confirmation route, or cancellation, the prepared state is immediately dropped (and `ToolBatch::resolve_at` atomically clears call attachments on resolution, while cancellation clears pending attachments across the batch) without ever reaching `execute`.
4. **`execute` (Causa `dispatch`)**: `Tool::execute` borrows the attached `PreparedWrite`, `(PreparedCommand, ExecutionGrant)`, or validated script source from `ToolCallContext::attachment()`—with no second JSON decode and no second `CommandRuntime::check`—and Causa clears the call's attachments atomically when the result resolves.

- **Allow this time**: file versions are re-checked at execution before writing the temporary file, and for existing-file overwrites the target's metadata (`device id`, `inode`, `size`, `mtime`) and regular-file type are checked a second time after syncing the temporary file and immediately before `renameat`. A mismatch, a deleted target, a non-regular replacement, or an occupied new target results in `Failed` (with the temporary file cleaned up) and the file is untouched. This detection is best-effort: a tiny POSIX window remains between the pre-rename `statat` check and `renameat` (since POSIX offers no atomic compare-and-replace primitive and external processes do not obey TARS's locks), so an external modification occurring inside that window will be overwritten.
- **Reject**: an optional one-sentence reason can be attached. The model receives Rejected (`user declined this write`) plus the reason; this is an ordinary tool result, the round continues and the file is untouched.
- For `write_file`, `edit_file`, and MCP calls, "Always allow for this session" is not offered; switch the permission mode when confirmation-free writes are needed. For `run_command`, prefix-based command approval rules and confirmation options apply (see [Command approval rules](#command-approval-rules)).

Waiting for confirmation does not count against a single tool's execution deadline (default 10 seconds) but is still bounded by the remaining work deadline; when the deadline arrives the round is cancelled, the call is recorded as not executed and the file is untouched. TUI `Esc` or CLI `Ctrl-C` also ends the wait.

- **CLI**: when stdin and stderr are both terminals and input does not come from `--stdin`, the diff is printed to stderr and one line of `y`/`n` is read (also `yes`/`no`); a rejection may be followed by a one-sentence reason. The stdout report format is unchanged. When not a terminal, `ask` does not block and returns Rejected immediately (no confirmation channel is available), the process ends normally and the file is untouched.
- **TUI**: the confirmation panel shows the tool name, path and a scrollable diff; `Enter` / `y` allows, `n` rejects with an optional reason, and `Esc` / `Ctrl-C` cancels the round. The accidental-key guard window and other panel details are in [TUI](tui.md).

The initial mode is chosen when creating a session through the preset `permission_mode`, CLI `--permission-mode` or the TUI new-session form. While running:

- In the TUI, `/mode <name>` switches, and `Shift-Tab` cycles between `read-only`, `ask` and `accept-edits`. `full-access` is not in the cycle and can only be entered with `/mode full-access`.
- CLI `session run --permission-mode <name>` changes and saves the current mode.
- A switch affects only calls whose decision is made afterwards, including calls in the current batch that have not yet reached their turn to ask; a confirmation already displayed still waits for the user's answer.
- The current mode is saved with the record and restored on reopen; when it is currently `full-access` and the initial mode was not, reopening yields `ask`.
- Mode switches are not written into Context; the model learns that the current mode disallows something only from the body of a Rejected result.

### Command approval rules

`run_command` supports prefix-based permission rules across two persistent layers plus an in-memory session layer:

1. **User rules (read-only, trusted by default)**: `<user_tars_dir>/permissions.toml` (`$TARS_HOME/permissions.toml` when `TARS_HOME` is an absolute path; otherwise `~/.tars/permissions.toml` on Unix/macOS or `%USERPROFILE%\.tars\permissions.toml` on Windows). Skipped when `--no-config` is passed. User rules live outside the command sandbox's write scope and are trusted automatically without a confirmation prompt. **TARS never creates or modifies the user rules file automatically.**
2. **Workspace rules (workspace-private, Store-trusted)**: `<workspace_root>/.tars/permissions.toml` (only at the workspace root, never searched in parent directories). `.tars/` is a workspace-private gitignored directory; when TARS writes workspace rules for the first time, it ensures `.tars/.gitignore` (containing `*`) exists without overwriting an existing `.gitignore`.
3. **Session rules (in-memory only)**: added from the confirmation panel (`Allow for this session`). Kept strictly in memory for the current open session, never written into `tars-session-v2.4` records, and automatically cleared when the session closes or reopens (including rules with `outside_sandbox = true`).

#### Rule file format, limits, and validation

```toml
# .tars/permissions.toml or ~/.tars/permissions.toml
version = 1

[[command]]
prefix = ["cargo", "test"]
decision = "allow"            # allow | ask | deny

[[command]]
prefix = ["git", "push"]
decision = "allow"
outside_sandbox = true        # also allow outside_sandbox = true calls; valid only with allow

[[command]]
prefix = ["rm", "-rf"]
decision = "deny"
```

- `version` must be `1`. Unknown fields, duplicate keys, wrong types, empty `prefix`, empty or NUL-containing prefix words, and `outside_sandbox = true` combined with `ask` or `deny` all fail validation.
- Each rules file is bounded to **256 KiB** and **1000** `[[command]]` entries.
- Single-word `decision = "allow"` rules targeting an interpreter or wrapper command are rejected (`deny` and `ask` are unrestricted). The forbidden single-word `allow` list is: `bash`, `sh`, `zsh`, `env`, `xargs`, `find`, `sudo`, `eval`, `exec`, `command`, `nohup`, `time`, `timeout`, `nice`, `python`, `python3`, `node`, `ruby`, `perl`.
- Invalid user or workspace rule files fail session creation or opening immediately with the file path and 1-based line/column without echoing rule values; missing files simply contribute no rules.

#### Conservative command parsing and cross-layer merging

TARS parses `command` with a conservative built-in parser without invoking a shell:

- **Recognized syntax**: unquoted words, single-quoted strings, double-quoted strings without `$`, backticks, or `\`, connectors (`&&`, `||`, `;`, `|`, newlines), and the fixed redirections `2>&1`, `>/dev/null`, and `2>/dev/null`.
- **Unmatchable syntax** (falls back to the active permission mode without applying rules): `$`, backticks, any other redirection, background `&`, parentheses `(...)`, braces `{...}`, glob characters (`*`, `?`, `[`), leading `~`, heredocs, leading `VAR=val` assignments, comments `#`, or unclosed quotes.
- A rule matches a simple command segment iff the segment's unquoted leading words match `rule.prefix` word-for-word literally (`git` does not match `/usr/bin/git`).
- All three layers (`user`, active `workspace`, `session`) are merged by union across all segments with strict precedence **`deny > ask > allow`**:
  1. If any segment matches `deny` in any layer, the whole command is `deny`.
  2. Else if any segment matches `ask` in any layer, the whole command is `ask`.
  3. Else if every segment matches `allow` (and for `outside_sandbox = true` requests, every segment's `allow` match has `outside_sandbox = true`), the whole command is `allow`.
  4. Otherwise no rule decision applies. Workspace or session `allow` rules can never override a user-level `deny` or `ask`.

#### Combination with permission modes

The base verdict from the mode table above is adjusted by the merged rule outcome identically during both the zero-I/O fast gate and the post-prepare live re-evaluation in `ToolPolicyProcessor`:

| Merged rule result | Adjustment to mode verdict |
| --- | --- |
| `deny` | Always Rejected without prompting, in every mode including `full-access` (model sees only the rule scope, never other rules) |
| `ask` | Turns `execute` into `ask` (prompts the user; Rejected when no confirmation channel is available) |
| `allow` | Turns `ask` into `execute` directly (issuing an `ExecutionGrant` with `allow_outside_sandbox = true` when `outside_sandbox = true`); `read-only` stays Rejected |
| None | Unchanged |

#### Protection, trust, and confirmation options

- **Dual-layer read-only protection**: `<workspace_root>/.tars/` and any in-workspace session store directory are read-only to sandboxed `run_command` and rejected by `write_file` / `edit_file` in all permission modes (including `full-access`).
- **Workspace trust check**: cloned repositories may still commit `.tars/permissions.toml`, so TARS checks the file byte-for-byte against a trusted snapshot stored per canonical workspace root in `<store>/tars.db` (`workspace_trust` table, `kind = "permissions_toml"`).
  - When a workspace rules file is new or modified, its `deny` and `ask` rules activate immediately, while its `allow` rules remain ignored until trusted.
  - The TUI displays a trust prompt (with a 0.5s accidental-key guard, `[OUTSIDE SANDBOX]` warnings, and unified diff when previously trusted); the CLI prints the ignored `allow` rule count to stderr and accepts `--trust-workspace-rules` on `session create` and `session run`.
  - Transient `tars run` has no Store, so untrusted workspace `allow` rules remain ignored (user rules and workspace `deny`/`ask` rules still apply).
- **Four-option command confirmation (CLI & TUI)**:
  - When the command is conservatively parseable (and when starting with an interpreter/wrapper from the forbidden single-word list, suggests the full command segment):
    1. **Allow once** (`1` / `y` / `Enter`);
    2. **Allow for this session** (`2` / `s` — adds in-memory session rules only);
    3. **Always allow in this workspace** (`3` / `w` — shown only when a workspace root, Store, and trusted workspace state exist; verifies `.tars/permissions.toml` on disk still matches the session's trusted snapshot to prevent TOCTOU tampering, creates `.tars/.gitignore` `*` if missing, preserves all existing bytes and comments verbatim while appending `[[command]]` blocks, validates with the strict parser, writes atomically, and updates the Store trust copy);
    4. **Deny** (`n` / `4` when 4 options / `3` when 3 options, with optional reason).
  - When workspace rules are untrusted or no Store exists, option 3 (`w`) is omitted and ignored. When the command is unmatchable or a single-word interpreter, only **Allow once** and **Deny** are offered. Requests with `outside_sandbox = true` clearly warn that the saved rule will include `outside_sandbox = true`.
- **Provenance display**: tool progress in the TUI and stderr notices in the CLI report the governing rule source (`allowed by ...`, `denied by ...`, `asked by ...`).

#### Residual risks for command rules

- Prefix rules do not constrain trailing arguments: for example, allowing `git` or `cargo test` permits flags such as `git -c ...` or project build scripts, and combining `allow` with `outside_sandbox = true` grants unconfined host execution (including access to `.tars/`, `~/.tars/`, and the Store) for matching prefixes.
- Conservative parsing falls back to asking on unmatchable syntax such as `>` redirections (`cargo test > out.txt`).
- Every machine and Store must independently trust a repository's `.tars/permissions.toml` before its `allow` rules activate; an external mid-session edit to `.tars/permissions.toml` causes in-session workspace-rule appending to refuse overwriting or blindly trusting the modified file.

## Find files tool (`find_files`)

`find_files` provides pure-Rust, handle-relative regular-file discovery across the workspace on both macOS and Linux without requiring external `rg` or a command sandbox. It runs inside the same `WorkspaceTools` concurrency slots and `call_timeout_secs` deadline as `list_directory` and `read_file`.

- **Parameters (all optional)**: `path` (workspace-relative starting directory, defaulting to `.`; rejects `..`, `\`, NUL, absolute paths, and `.git`/`.hg`/`.svn`/`.jj` components case-insensitively), `pattern` (linear-time `globset` pattern of `1..=256` bytes without CR/LF/NUL; without `/` matches file basenames, with `/` strips leading `./` and matches relative to `path`; invalid glob syntax is `Rejected` before execution), `max_results` (`1..=limits.max_search_matches`, default `200`), `max_depth` (`1..=limits.max_search_depth`, default `32`, where `1` means immediate children of `path`), `ignore_case` (default `false`), and `include_ignored` (default `false`).
- **Ignore rules and VCS exclusion**: When `include_ignored` is `false`, `find_files` walks from the workspace root down to `path` via `Workspace::child_directory` and loads `.gitignore` followed by `.ignore` via `Workspace::child_file` (bounded to 64 KiB; missing, symlinked, non-regular, non-UTF-8, or oversized ignore files are skipped safely) so nested `path` queries inherit root ignore rules. Ignore rules honor comments, `#`/`!`/space escapes, negation (`!`), trailing-`/` directory-only rules, anchored vs unanchored patterns, and `.ignore` precedence over `.gitignore` in the same directory, pruning ignored directories before descending. `.git`, `.hg`, `.svn`, and `.jj` (case-insensitive) are unconditionally excluded even when `include_ignored = true`.
- **Symlink safety, deterministic order, and ceilings**: traversal uses `Workspace::child_directory` (`O_NOFOLLOW | O_DIRECTORY | O_CLOEXEC` and `st_dev` verification) and `statat(..., SYMLINK_NOFOLLOW)` fallback for `FileType::Unknown`, skipping symlinks and special files. Entries within each directory are sorted lexicographically and traversed in deterministic BFS order up to `max_depth`, returning workspace-relative paths without leading `./`. Traversal enforces `max_results` (`limit_reason = "max_results"`), `max_output_bytes` (`"output_bytes"`), and a hard `100,000` visited-entries ceiling (`"visited_entries"`), recording up to 32 non-fatal per-directory I/O or non-UTF-8 entry errors in `issues` (`complete = !truncated && issues.is_empty()`).

## Search tool

`search_text` launches the resolved `rg` in a read-only sandbox; the process runs with the workspace root as its working directory and a cleared environment (only `PATH`, `HOME` and `LANG`, plus a session-private `TMPDIR`, `TERM=dumb` and `NO_COLOR=1`). The policy is the `Roots` read scope: the workspace, the private temporary directory and the executable's own directories are readable, only the private temporary directory is writable, network access is denied, and the sandbox's credential denials still apply. One session runs one search at a time.

TARS assembles every argument; model text appears only after `--` in the query and inside `--glob=` values. Fixed flags are `--no-config --json --stats --hidden --no-ignore-global --no-ignore-parent --no-require-git`, followed by `--fixed-strings` unless `regex` is true, the case flag, optional `--context=N`, optional `--no-ignore`, `--max-depth`, `--max-filesize`, 1 MiB regex/DFA limits, the model `--glob` and the four version-control exclusions `--iglob=!.git`, `!.hg`, `!.svn`, `!.jj` (emitted last, so a model glob cannot re-include them; without a trailing slash so a submodule's `.git` file is excluded too, and case-insensitive like the default macOS filesystem). PCRE2 (`-P`), `--pre`, `--search-zip` and a user configuration file are never used, and global or parent ignore files outside the workspace are unreadable in the sandbox, so results depend only on the workspace contents.

- **Parameters**: `regex` (default false, literal matching), `ignore_case` (default false), `glob` (one glob, at most 256 bytes), `context_lines` (0–3, adds `before` and `after` to each match), and a `path` whose component is `.git`, `.hg`, `.svn` or `.jj` is rejected before `rg` starts, because `rg`'s exclusion globs do not apply to an explicit root, `include_ignored` (default false; still excludes the version-control directories) and `max_matches`. A query containing a newline, a query or glob that `rg` rejects, and an oversize regular expression are Rejected with the reason. `path` is opened through the workspace handle first and must be a directory or a regular file; a missing path is Failed and an outside or FIFO path is Rejected before any process starts.
- **Limits**: `max_matches` stops reading and terminates the `rg` process tree (`complete=false`, `limit_reason=max_matches`); the serialized result stays within `max_output_bytes`; `max_search_depth` becomes `--max-depth`; `max_file_scan_bytes` becomes `--max-filesize`, so a larger file is skipped entirely. `max_search_files`, `max_search_scan_bytes` and the old 4000-entry ceiling no longer bound search because `rg` has no equivalent; they remain in the saved definition so old records keep loading, and the call deadline bounds the total work.
- **Results**: `matches` carry `path`, one-based `line`, `text` and `snippet_truncated`, plus `before`/`after` when context is requested; `issues` holds at most 32 `rg` stderr observations and makes `complete=false`; `scanned_files` and `scanned_bytes` come from `rg`'s end-of-run statistics and are `null` when it did not finish normally. `scanned_entries` is always `null` and `skipped` counts reported issues, because `rg` performs its own skipping and does not report a count. `rg` exit status 2 with no matches is Rejected with its message; a normal exit with or without matches is Succeeded.
- **Availability**: a missing sandbox backend or an unready `rg` rejects every call, names the missing piece and starts no process; the search tool never falls back to in-process matching or to running without a sandbox. macOS (Seatbelt) and Linux (`bwrap` + `seccomp-BPF`, requiring `bubblewrap` and unprivileged user namespaces) support `search_text`, while Windows currently fails closed; sessions containing `search_text` still open when unavailable and reject each call with the reason. The TUI startup check reports the same state (see [TUI](tui.md)).
- **Residuals**: symbolic links are never followed, matching the previous behavior; `rg`'s own binary-file detection and ignore implementation decide which files are searched; the `Roots` read scope makes global and parent ignore files unreadable instead of ignored, and the whole-machine read scope with `network = "open"` applies to `run_command` only.

## Command tool

`run_command` launches `/bin/bash -c <command>` inside the platform sandbox (macOS Seatbelt or Linux Bubblewrap `bwrap` + pure-safe-Rust cBPF `seccomp-BPF`). `command` is non-empty, at most 16 KiB and rejects NUL; the optional `workdir` is resolved component by component as a workspace-relative path and rejects escapes; the optional `timeout_secs` defaults to 120 and is at most 600, and the session definition can only lower it. The optional `outside_sandbox: true` with `justification` (at most 1 KiB of UTF-8 bytes, non-empty, NUL rejected) requests running this one command outside the sandbox; the tool description asks the model to use it only when the command was blocked by the sandbox and outside writes, credentials or network are genuinely needed, and TARS does not verify that it was actually blocked. stdin is `/dev/null`, no TTY is allocated, and no shell profile/rc is read. The environment keeps only `PATH`, `HOME` and `LANG`, plus a session-private `TMPDIR`, `TERM=dumb` and `NO_COLOR=1`; sandbox-outside runs also clear the environment, but files, network and signals are unrestricted and the session's `network` setting no longer applies. One session executes only one command at a time and other calls queue, with queue time counted against their own deadlines.

Output merges stdout and stderr; over the result budget the beginning and end are kept and the omitted byte count is reported; invalid UTF-8 and control characters are cleaned; empty output is `(no output)`. A shell exit (including non-zero) is Succeeded with an `exit_code`; when the direct process is killed by a signal it also carries `signal` and `128+signal` (under Linux `bwrap --unshare-pid`, an inner shell killed by a signal exits `bwrap` with `128+signal` and no host-level `signal` field). A command's own timeout is TimedOut and cancellation is Cancelled, both carrying the output received so far and "may have partially executed"; argument, path, unavailable sandbox, missing justification for a sandbox-outside request or denied permission are Rejected without starting a process; failure to start a process is Failed. Sandbox-outside results additionally carry `outside_sandbox: true`. Commands never continue as background jobs and offer no interactive stdin/TTY; complete output is not written to disk.

The sandbox denies by default and then allows: reads and writes of the workspace and the private temporary directory; whole-machine/system read-only (`Host` scope includes the user home directory, `/Applications` and `/private/var` on macOS, or system trees plus `$HOME` on Linux); `/dev` allows only `/dev/null`, `/dev/zero`, `/dev/urandom` and `/dev/random` (plus `/dev/fd` on Linux `bwrap`), and reading `/dev/tty` fails; when the current store directory (`DIR/sessions`) is outside the workspace and does not overlap the private temporary directory, it is denied for both reads and writes, whereas an in-workspace store directory (`DIR/sessions`) and `<workspace_root>/.tars/` are kept read-only with their entry, intermediate ancestor directories and subtree non-writable/non-renamable/non-deletable (and when `DIR/sessions` equals or wraps the workspace root, the entire workspace is read-only). Credential locations deny both reads and writes, including `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.azure`, `~/.config/gcloud`, `~/.kube`, `~/.docker`, `~/.config/gh`, `~/.password-store`, `~/.zsh_sessions`, `~/Library/Keychains`, `/Library/Keychains`, `/Library/Preferences/SystemConfiguration`, and Linux `~/.local/share/keyrings` / `~/.config/sops`, as well as files such as `~/.netrc`, `~/.git-credentials`, `~/.config/git/credentials`, `~/.npmrc`, `~/.pypirc`, `~/.gem/credentials`, `~/.cargo/credentials.toml`, `~/.cargo/credentials`, `~/.vault-token`, `~/.terraform.d/credentials.tfrc.json`, `~/.pgpass`, `~/.my.cnf`, the AI tool tokens `~/.codex`, `~/.gemini`, `~/.config/github-copilot`, `~/.claude.json` and `~/.claude/.credentials.json`, the histories `~/.zsh_history`, `~/.bash_history`, `~/.python_history`, `~/.node_repl_history`, `~/.psql_history`, `~/.mysql_history`, `~/.sqlite_history` and `~/.local/share/fish/fish_history`, and the shell startup files `~/.zshenv`, `~/.zprofile`, `~/.zshrc`, `~/.zlogin`, `~/.bashrc`, `~/.bash_profile`, `~/.bash_login`, `~/.profile`, `~/.config/fish/config.fish` and `~/.config/fish/fish_variables`, where model API keys are usually exported (a sandboxed `bash -l` therefore prints an error or reads `/dev/null` for its profile and continues; zsh skips missing/empty files); the same applies when the workspace happens to equal the home directory. In the workspace root's `.git`, `hooks`, `config`, `config.worktree`, `modules` and `worktrees` are read-only, and `.git` itself cannot be deleted or renamed (and cannot be created on macOS); objects, refs, index and logs remain writable, and git running outside the sandbox is unaffected by these limits. A nested repository's `.git` is outside the protection scope. Network is disabled by default (including loopback, DNS, `AF_UNIX` and `AF_VSOCK` sockets; Linux overlays `--unshare-net` and `seccomp-BPF`); `network = "open"` allows only IP egress and system DNS (`mDNSResponder` on macOS, `/etc/resolv.conf` / `systemd-resolved` DNS on Linux), while host unix sockets (`AF_UNIX` / `AF_VSOCK`, `ssh-agent`, Docker) and `io_uring`/`ptrace`/`bpf`/`kexec_load` are still denied (Linux preserves `socketpair` for internal IPC). Signals can only be sent to processes inside the sandbox (enforced on Linux via PID namespace + `--die-with-parent` + `--new-session`, reporting all 5 capability dimensions `full`). On Linux, `bwrap` and unprivileged user namespaces are required; on Ubuntu 24.04+ with `kernel.apparmor_restrict_unprivileged_userns = 1`, load an AppArmor `userns` profile for `/usr/bin/bwrap`. A single command can request running outside the sandbox, and the permission table decides whether to ask or execute directly; without the request the command always stays inside the sandbox. When the sandbox is unavailable, creating a session with `run_command` fails; reopening a saved session rejects every call with a reason, and sandbox-outside requests are likewise not offered. Windows has no backend and cannot create a new session with the command tool.

The TUI `/status` shows the full backend and each dimension as `Commands: <backend>: ...`; on open, a one-line notice explains when the sandbox is unavailable. CLI `session create` prints the full status to stderr; `tars run` and `session run` print a short status without the full dimensions. The confirmation panel for sandboxed commands shows the full command, working directory, deadline, network policy and "workspace writable, `.git` hooks and configuration read-only, credentials unreadable"; a sandbox-outside request instead shows a prominent "not in the sandbox: whole machine readable/writable, network reachable, credentials readable" and displays the model's justification, no longer showing the session's network setting. Permission rules are in the previous section.

The configuration uses the `network`, `default_timeout_secs` and `max_timeout_secs` of `[profiles.NAME.command]`, which take effect only when the preset includes `run_command`; CLI `--command-network` overrides the network. The TUI new-session form shows a read-only summary for the current Tools selection. The saved definition freezes the complete values, and reopening does not follow global configuration changes.

Residuals (not claimed to be eliminated):

- Descendants that actively call `setsid()`/`setpgid()` can escape the process group and are still constrained by the sandbox policy; TARS only cleans up known process groups when it exits.
- Commands still running may be left behind when TARS is `SIGKILL`ed.
- A process group id has a very small reuse window after the leader exits; when a descendant holds the pipe, the reader thread may detach after 2 seconds.
- `sysctl-read` still allows names other than `kern.proc*`; the `kern.proc*` and process-info restrictions only prevent reading other processes' environments.
- After whole-machine reads are allowed, secrets outside the credential list remain readable: tokens written in `~/.cargo/config.toml` or `~/.gitconfig`, `.env` files outside the project, and browser configuration directories not protected by TCC are not in the list; existing TCC grants for the terminal such as "Documents" and "Desktop" apply to commands as well.
- `.git` protection covers only the workspace root's `.git`: it locks hooks, config, modules, worktrees and `.git` itself; nested repositories are not protected. Commands can still rewrite objects, refs, index and logs and can corrupt the repository content, but cannot use that to execute code outside the sandbox. When `.git` points outside the workspace (a linked worktree), all sandboxed git writes fail; submodule operations and configuration-changing operations such as `git config` and `git remote add` fail as well.
- Under `network = "open"`, operations that need credentials (git over SSH, private registries) fail because credentials are unreadable; a command can list `/private/var/run` to find the ssh-agent socket but cannot connect to it.
- Whether a command was blocked by the sandbox is declared by the model itself and not verified by TARS; under `full-access` the model can request sandbox-outside execution at any time. A command granted `outside_sandbox: true` runs unconfined with the user's host write privileges and can still modify host files, including `<workspace_root>/.tars/` and the session store directory. Sandbox-outside runs still clear the environment, so model credentials never enter the command environment.
- On Linux `bwrap`, non-existent protected paths (such as `.git` or `.tars/` before they exist on disk) are **not** pre-created as host stubs so the workspace and `git status` stay clean; instead, write tools reject `.git`/`.tars` independently and Store trust checks validate `.tars/permissions.toml` / `.tars/agents/*.md`. Linux bind-mounts also skip symlink entries in `read_only_subpaths` / `protected_entries` (because bind-mounting a symlink dereferences it and would expose external targets; in-workspace symlink targets are resolved and protected separately), and individual denied files are masked read-only with `/dev/null` (so reads see an empty file and writes fail) while denied directories are masked with an empty `0000` `tmpfs`.
- Binding the command tool runs probes for the Roots and Host policies in sequence, which increases startup time; a failed probe still disables the whole tool.

## Limits

| Effective limit | Default and hard limit |
| --- | --- |
| Actual file operations per session / whole host | 4 / 16 |
| Single tool execution deadline (excluding confirmation wait) | 10 seconds, also bounded by the remaining work deadline |
| Complete serialized tool result | 64 KiB |
| Directory entries | 200 |
| Single-file scan | 2 MiB |
| Search directory depth / matches | 32 / 200 |

`max_search_files`, `max_search_scan_bytes` and the 4000-entry ceiling remain in `[profiles.NAME.tool_limits]` for saved-record compatibility but no longer bound `search_text`, which is limited by `max_search_depth`, `max_file_scan_bytes`, `max_matches`, the result budget and the call deadline instead. `search_text` also keeps its own single-permit queue, separate from the file-operation slots.

| Write limit | Default and hard limit |
| --- | --- |
| Editable file size / written content size | 2 MiB / 1 MiB |
| Segments in one `edit_file` | 32 |

A preset can lower effective limits (results no smaller than 1024 bytes), and tool arguments can only lower them further; neither presets nor arguments can raise a hard limit. `[profiles.NAME.tool_limits]` controls the general limits above, and `[profiles.NAME.write_limits]` controls the three write limits; the fields are in [Configuration](configuration.md). Skipped prefixes, long lines and JSON escaping all count toward the limits; scanning and output are bounded while being produced rather than collecting all results first and then trimming. In particular, `read_file` accounts for exact `serde_json` per-character string escaping (2 bytes for `"`, `\`, `\n`, `\r`, `\t`, `\x08`, `\x0c`; 6 bytes for other `< 0x20` control characters; UTF-8 byte length for other characters including non-ASCII) alongside path escaping and a 1024-byte metadata reserve against `max_output_bytes`. In persistent sessions, tool results that still exceed the entry-point spill threshold (4,000 estimated tokens) are persisted into the SQLite `artifacts` table of `<store>/tars.db` with a real-line preview while keeping structured metadata fields intact; see [Long-session compaction](configuration.md#long-session-compaction). Directory traversal for `list_directory`, `read_file`, and `find_files` uses directory handles bounded with depth; `search_text` has no in-process traversal and is bounded by the `rg` flags and the call deadline instead.

The Causa executor uses the same saving deadline as a timeout fallback for call waits; deadlines and cancellation also take effect at queueing and file-operation checkpoints; dropping a tool future requests that the corresponding operation stop. Each work's blocking tasks are supervised by a TaskTracker, writes are retained until the real closure exits, and both terminal state and close wait for them to settle. This mechanism cannot forcibly preempt stuck OS I/O and does not guarantee bounded exit on network or abnormal filesystems.

## Observation, saving and legacy records

The TUI distinguishes Waiting, Running, Returned (materials pending commit), Committed, plus work terminal state and save state. A lost observation is reported and corrected with the reliable terminal-state summary. Each work retains at most 128 call summaries, with name/argument summaries at most 128/256 bytes each; after cancellation, the UnknownOutcome actually returned by Causa is kept; once all real file tasks have exited, the application distinguishes calls that started but produced no accepted result from calls not executed while waiting for confirmation. This projection never modifies the original batch or committed results, and a committed unknown result still retains the material-commit fact. Summaries do not consume the original uncommitted ToolBatch and are not a persistent work ledger. `/tools` or F6 expands full calls and results from the actual material cache; terminal control characters are handled only at display time.

CLI execution stdout still outputs only the final text or the existing JSON report; tool materials can be inspected through save/export. Retrying a failed save reuses the original materials and never reruns tools or the model. Reopening can show originally committed calls/results but does not restore or execute old work. Cancellation may leave only a committed declaration, with the result still in the original uncommitted batch; saving never fabricates a paired result. New input that meets unpaired materials is returned as-is. TUI F7 / `/repair` can preview accepting the original result or removing the unpaired declaration, and CLI `session repair` can remove it explicitly; send new work only after applying and saving. UnknownOutcome and the original work state stay unchanged; the full conditions are in [Continuation after interruption](session-continuation.md).

When a write is cancelled halfway through, Causa reports UnknownOutcome; atomic writing guarantees that the file is either the old content or the new content. The repair preview marks these calls with "the file may have been written; read it again before continuing". Accepting the original result is supported only for built-in tools from the formal assembly (four read-only, two write and one command tool); a batch containing MCP or other non-built-in calls can only be removed, with a notice that external side effects may already have happened.

The legacy JSON format `tars-session-v2.4` is no longer written as primary storage (sessions are stored in SQLite `<store>/tars.db`). Validated `tars-session-v2.4` JSON records can be imported explicitly into SQLite as single-root-agent sessions via `tars session import-legacy --record ./old-record.json --store ./data`, and standalone Context materials can still be extracted offline via `tars session export-materials`. Older records (`tars-session-v2.3`, `tars-session-v2.2`, `tars-session-v2.1`, `tars-session-v2` and v1) remain rejected explicitly with `StoreError::UnsupportedFormat`, with no automatic old-file rewriting:

```sh
tars session import-legacy --record ./old-record.json --store ./data --json
tars session export-materials --record ./old-record.json --output ./materials-new.json
tars session create --store ./data --provider openai-chat --model "$MODEL_ID" \
  --load ./materials-new.json --json
```

Export reads at most 64 MiB and the target must not exist; it reads no credentials, calls no model and reuses no old definition. When creating the new session, tools and workspace must still be selected explicitly if tools are needed.

## MCP tools

MCP tools do not go through the workspace directory handles and are therefore not constrained by the path boundaries above. Configuration, selection, approval levels, environment isolation and lifecycle are in [Configuration](configuration.md#mcp-servers). Servers run with the user's privileges; limiting them relies only on permission modes and `approval` rejecting calls, never on the workspace boundary or an OS sandbox.

## Code execution (`run_code`)

When `code_execution` is enabled for a new session (via `[code_execution]`, `[profiles.<name>.code_execution]`, CLI `--code-execution`, or the TUI new-session form), `assembly` registers the built-in read-only `run_code` tool whenever at least one read-only workspace tool (`list_directory`, `read_file`, `search_text`, `find_files`), `recall`, or an `mcp` runtime is bound; if none of those are bound, `run_code` is omitted rather than advertising an empty shell.

- **Runtime and isolation**: Powered by `rquickjs 0.14.0` (QuickJS-NG ES2020) compiled with `default-features = false, features = ["futures"]` (preventing Promise-interrupt stdout noise in `--json` and TUI output) and zero `unsafe` in TARS code. Each invocation runs statelessly (variables do not persist across calls) inside an `(async () => { ... })()` wrapper on a `spawn_blocking` single-threaded Tokio runtime + `LocalSet`, with `process`, `require`, `fetch`, `import()`, and filesystem/network globals absent. If `return` is omitted, bounded `console.log` / `console.warn` / `console.error` output is returned.
- **Read-only subcall whitelist and progressive MCP discovery**:
  - Bound built-in read-only helpers (`list_directory`, `read_file`, `search_text`, `find_files`, `recall`) are exposed on both global scope and `tools.*`, accepting an options object or positional arguments (`find_files()` with no arguments defaults to `{}`). `await tools.list()` returns summaries (`{ name, description, source }`) of all bound built-in read-only tools and currently `KnownReadOnly` MCP tools (`approval = "writes"`, `read_only = true`, `destructive != true`); `await tools.describe(name)` returns full `{ name, description, parameters, source }` metadata (throwing on unknown or non-read-only tools); `await tools.call(name, args)` invokes a bound built-in or `KnownReadOnly` MCP tool.
  - Every `tools.call` to an MCP tool re-verifies `McpPermissionTable` in real time right before dispatch (and refreshes stale listings when a server sent `tools/list_changed`): if a tool was downgraded to `McpPrompt` / `McpApprove` or removed, the call is rejected immediately even if the script cached the name. `run_code`'s `ToolDefinition` (`code: string`) stays static for the entire session to preserve prompt caches across MCP catalog refreshes.
  - Write, command, skill, and recursive calls (`write_file`, `edit_file`, `run_command`, `load_skill`, `run_code`, `McpPrompt`, `McpApprove`) are never bound or callable inside the sandbox.
  - `list_directory`, `read_file`, `search_text`, and `find_files` subcalls execute through the session's real `WorkspaceTools` (preserving handle-relative `O_NOFOLLOW` path checks, sandboxed `rg`, limits, and concurrency permits) and update the shared `observations` table so a `read_file` inside `run_code` satisfies subsequent direct `edit_file` / `write_file` read-before-write checks.
- **Processor chain layering**: The outer `run_code` call passes through the full `before` (`ToolPolicyProcessor`, classifying as `KnownReadOnly` so all four permission modes execute without approval) and `after` (`OutputSpillProcessor` in persistent sessions, spilling large outputs to the SQLite `artifacts` table while preserving `stats` inline) chains and emits one top-level `ToolReporter` entry. Inner subcalls do **not** pass through `ToolBatchProcessor` (`before`/`after`), do not write to the 128-entry `ToolProgressSnapshot`, and never trigger inner artifact spills.
- **Resource guardrails and uncatchable abort**: `CodeExecutionSettings` defaults and validated bounds are `timeout_secs = 30` (`1..=120`, with `ToolExecutor` `call_timeout` given `timeout_secs + 5` headroom), `memory_limit_bytes = 32 MiB` (`4 MiB..=64 MiB`), `stack_limit_bytes = 512 KiB` (`64 KiB..=1 MiB`), `max_subcalls = 256` (`1..=512`), `max_concurrency = 8` (`1..=16`), and `max_output_bytes = 32 KiB` (`1024..=64 KiB`). Exceeding `max_subcalls`, wall-clock `timeout_secs`, or outer `CallControl` cancellation triggers both a fatal flag and the QuickJS interrupt handler so even `try { ... } catch {}` or `while (true) {}` aborts immediately without executing further subcalls. Returns `{ output, truncated, stats: { subcalls, by_tool, max_in_flight, duration_ms } }` (plus `error` on failure).

## Multi-agent collaboration tools

When multi-agent discovery is active (default on unless disabled), TARS exposes a pure event-driven four-tool collaboration surface (`spawn_agent`, `message_agent`, `read_agent`, `cancel_agent`) alongside the dynamic `<available_agents>` / `<model_profiles>` prelude section. All four tools are classified as `KnownReadOnly` on the caller side (`ToolPolicyProcessor` executes them without confirmation, while any write/command/MCP tool calls inside child agents still pass through their own narrowed `PermissionHub` and route interactive confirmations via `ApprovalsHub` with `[agent: <name>]` provenance) and reject unknown fields or spoofed identity/caller arguments (`additionalProperties: false`).

- **`spawn_agent`** (`agent`, `prompt`; optional `model` (`profile`, `id`, `reasoning_effort`, `temperature`, `max_tokens`), `background` (default `false`), `reusable` (default `false`), `on_parent_complete` (`"continue"` | `"cancel"`, default `"continue"`), `timeout_secs`, `max_rounds`):
  - **Synchronous (`background = false`)**: Shares the exact same `operations` admission, monotonic narrowing, and cancellation cascade path with `wake_policy = suppress_wake`, awaiting the child's committed terminal output in `ToolResult` (supporting parallel fan-out inside one Causa `ToolBatch`).
  - **Background (`background = true`)**: Atomically admits the child agent and operation in SQLite and immediately returns `{ agent_id, operation_id, status: "running" }`; on completion, results arrive via `agent_events` (`<task-notification>` mid-turn injection or 7-guard idle reactive wakeup).
- **`message_agent`** (`agent_id`, `prompt`; optional `background`, `on_parent_complete`, `timeout_secs`, `max_rounds`): Submits follow-up work to an existing idle `reusable` agent after validating capability compatibility and idle/repair-clean state; rejects busy, `single_work`, or repair-pending targets without implicit queuing and never resets delegation depth.
- **`read_agent`** (`operation_id`; optional `offset_bytes`, `limit_bytes` capped at 64 KiB): Returns the authoritative operation status and a UTF-8 boundary-safe slice of its saved archived output without re-executing, summarizing, or requiring credentials.
- **`cancel_agent`** (`operation_id`): Cooperatively cancels `operation_id` and all active descendants (`creating` or `running`) and awaits settlement without altering already-committed terminal states.

### Monotonic narrowing, presets, and `.tars/agents/*.md` trust gate

- **Monotonic permission narrowing (`child <= parent`)**: Child agents inherit the session workspace and cannot expand tools, permission mode, timeout, round limits, MCP servers, or command/write limits beyond the calling parent (`ChildNarrowingRequest`). Switching a child's `model.profile` or `model.id` only changes the model/generation parameters (validating `temperature` against `0.0..=2.0` / Anthropic `<= 1.0`) and never expands workspace or tool privileges.
- **Built-in presets and Markdown discovery**: `tars-core` compiles in `explore` (read-only subset: `read_file`, `list_directory`, `search_text`, `find_files`, `recall`, `run_code`) and `general` (inheriting parent-bounded capabilities). Additional presets are discovered from `~/.tars/agents/*.md` / `[agents].dirs` and `<workspace_root>/.tars/agents/*.md` (YAML frontmatter `name`, `description`, optional `tools`, `model`, `max_model_rounds`, `timeout_secs`, `default_interaction`, plus Markdown body as the child's frozen role system prompt).
- **SQLite `workspace_trust` (`kind = "workspace_agents"`)**: Workspace `<workspace_root>/.tars/agents/*.md` files are untrusted by default. Until explicitly trusted via CLI `--trust-workspace-agents` or the TUI workspace agents trust prompt, workspace presets are excluded from `<available_agents>` and rejected by `spawn_agent`; transient `tars run` sessions have no Store and always ignore workspace agent presets. Once admitted, a child agent's resolved `AgentDefinition` is frozen in SQLite so later edits to `.tars/agents/*.md` or `config.toml` do not affect replay or reopen.

## Workspace trust boundaries

TARS enforces two strictly isolated trust layers in SQLite `<store>/tars.db` (schema `user_version = 2`):

| Layer | SQLite table | Scope & lifecycle | Management |
| --- | --- | --- | --- |
| **Folder-level trust** | `trusted_workspaces` | Records canonical workspace directory paths and their SHA-256 hashes before creating or opening a default interactive TUI session (`FolderTrustWizard`). Preserved across `SessionStore::delete_session`. | Granted via TUI `FolderTrustWizard` (`Do you trust the files in this folder?`), inspected via TUI `/trust`, and listed or revoked via `tars trust list [--json]` and `tars trust revoke [DIR]` (defaults to the current directory and matches deleted directories via ancestor canonicalization). |
| **Content-hashed `.tars/` trust** | `workspace_trust` | Stores exact byte-for-byte `content_sha256` snapshots of `<workspace_root>/.tars/permissions.toml` (`kind = "permissions_toml"`) and `<workspace_root>/.tars/agents/*.md` (`kind = "workspace_agents"`). Preserved independently of `trusted_workspaces` and `sessions`. | Granted via the TUI `.tars/` trust prompts (with unified diff review and `0.5 s` accidental-key guard; `Enter`/`y` trusts, `n`/`Esc`/`Ctrl-C` declines) or CLI `--trust-workspace-rules` / `--trust-workspace-agents`; inspected via TUI `/trust` and `/rules`. |

**Isolation invariant:** Trusting a folder in `FolderTrustWizard` **never** writes `workspace_trust` rows, **never** activates `.tars/permissions.toml` `allow` rules or `.tars/agents/*.md` presets, and **never** bypasses the `.tars/` content-hash verification or diff confirmation prompts on first open or after any file modification. Likewise, revoking folder trust with `tars trust revoke [DIR]` removes only the `trusted_workspaces` entry and leaves `sessions` and `workspace_trust` intact.
